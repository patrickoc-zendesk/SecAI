# 22. Cheat Sheet

> [!info] Exam alignment
> **Domain:** All (1.0–4.0)
> **Purpose:** Last-48-hours rapid review. Every distractor pair, attack signature, and framework the exam loves. Read this the night before and the morning of.

## Exam at a glance

- **CY0-001** · up to 60 questions · 60 minutes · passing **600** / 900
- Domains: **1.0 Basic AI Concepts 17% · 2.0 Securing AI Systems 40% · 3.0 AI-assisted Security 24% · 4.0 AI GRC 19%**
- Question style: scenario-driven, "given X, pick the BEST control" — eliminate answers that don't fix the root cause.

## Domain 1 — fast facts

| Item | Remember it as |
| --- | --- |
| Supervised learning | Labeled data → predicts; classification/regression |
| Unsupervised learning | Unlabeled data → finds structure; clustering, dimensionality reduction |
| Reinforcement learning | Agent + reward signal → learns policy by trial and error |
| Fine-tuning | Adapting a pretrained model to a narrower task/domain |
| Epoch | ONE complete pass over the full training dataset |
| Pruning | Removing weights/connections to shrink a trained model |
| Quantization | Lowering numeric precision of weights (e.g., 32-bit → 8-bit) |
| Zero / one / multi-shot | 0 examples / 1 example / several examples in the prompt |
| System vs user prompt | System = policy/instructions from the app (trusted); user = input (untrusted) |
| LLM vs SLM | Billions of params, cloud, versatile vs millions-to-billions, on-prem/edge, cheaper + private |
| RAG | Retrieve trusted docs → inject into prompt → generate grounded answers |
| Embedding | Text → numeric vector capturing semantic similarity; stored in a vector DB |

### The 1.3 lifecycle stages (in order)

Business use case → data collection → data preparation → model development/selection → model evaluation → deployment → validation → monitoring and maintenance → feedback and iteration.
**Security is decided at the business-use-case stage and verified at every stage after.**

## Domain 2 — attack signatures (objective 2.6)

Given an incident, name the attack, then pick the compensating control.

| Attack | Signature | Primary compensating controls |
| --- | --- | --- |
| Prompt injection (direct) | Input contains instructions overriding the system prompt | Prompt firewall, prompt templates w/ delimiters, input/output filtering |
| Prompt injection (indirect) | Malicious instructions hidden in content the model processes (doc, page, RAG hit, tool result) | Treat external content as untrusted, output filtering, least privilege |
| Jailbreaking | Coercing the model past its safety training (role-play, hypotheticals, gradual escalation) | Model guardrails, guardrail testing, monitoring |
| Circumventing guardrails | Encoding/splitting/translating payloads to slip past filters | Robust filter testing, decode/normalize before filtering |
| Input manipulation | Crafted inputs (incl. other modalities) to trigger misbehavior | Input validation, modality limits |
| Data poisoning | Corrupted **training data** → bad model | Data verification + provenance, integrity controls |
| Model poisoning | Malicious manipulation of the **model/training process** (poisoned fine-tune, poisoned pretrained model) | Model evaluation, trusted registries, integrity checks |
| Backdoor/trojan | Model behaves normally until a **trigger** appears | Adversarial testing, model evaluation, monitoring |
| Introducing biases | Systematic unfair outcomes embedded (malicious or accidental) | Data balancing, bias audits, diverse evaluation sets |
| Model skewing | Selective data/feedback **shifts** model behavior over time | Monitor for drift, control feedback/retraining inputs |
| Transfer learning attack | Attack arrives via a poisoned/vulnerable **base model** being fine-tuned | Vet pretrained models, evaluate after fine-tuning |
| Model inversion | Reconstructing **training data/features** from outputs | Data minimization, anonymization, output limits |
| Membership inference | Determining **whether a specific record** was in the training set | Anonymization, minimization, DP-style protections |
| Model theft | Reconstructing/copying the **model itself** (bulk queries, distillation) | Rate limiting, token limits, access controls, watermarking |
| Sensitive information disclosure | Model leaks PII/secrets/system prompt in outputs | Data minimization, redaction, output filtering, guardrails |
| AI supply chain attack | Compromised model registry, dependency, or library | Signed models, provenance, SCA, vetted sources |
| Manipulating application integrations | A compromised integrated app/feed feeds the model malicious content | Validate integrated sources, isolate, monitoring |
| Insecure plug-in design | Over-privileged/unaudited tool plug-ins | Least privilege, allowlists, input validation |
| Insecure output handling | Downstream system **blindly trusts/executes** LLM output (XSS/SQLi via generated content) | Output encoding, validation, never execute model output raw |
| Output integrity attack | Attacker manipulates output so consumers act on **false data** | Integrity checks on outputs, source validation |
| Model DoS | Resource exhaustion: huge inputs, recursive/expensive generation | Rate limits, token limits, input quotas |
| Excessive agency | The **system** has too many permissions/tools and acts beyond intent | Least privilege, scoped tools, approval gates |
| Overreliance | **Humans** trust outputs too much and skip validation | Human validation, training, oversight |
| Hallucinations (as evidence) | Confident-but-wrong outputs; fabricated facts/citations | Grounding (RAG on trusted sources), confidence monitoring, human validation |

## The classic distractor pairs (know these cold)

| Pair | The distinction |
| --- | --- |
| Data vs model poisoning | Corrupted **data** vs manipulated **model/training process** |
| Model inversion vs membership inference | Reconstruct **data/features** vs "was **this record** trained on?" |
| Model inversion vs model theft | Steal **data** vs steal the **model** |
| Excessive agency vs overreliance | **System** over-permissioned vs **humans** over-trusting |
| Insecure output handling vs output integrity | Downstream fails to **treat output as untrusted** vs attacker **alters the output** |
| Prompt injection vs jailbreaking | Overriding instructions via **input content** vs coercing past **safety training** |
| Misinformation vs disinformation | False content spread (intent irrelevant) vs **deliberately created** to deceive |
| Data lineage vs data provenance | **Lifecycle/transformations** of the data vs its **origin/ownership** |
| Masking vs redaction | Replace with placeholder/fake value vs **remove/destroy** the sensitive content |
| Anonymization vs pseudonymization | **Irreversible** PII removal vs reversible (re-identification key exists) |
| Pattern recognition vs anomaly detection | Matches **known** signatures vs flags **deviations** from baseline |
| Human-in-the-loop vs oversight vs validation | Human **acts inside the process** vs **supervises/monitors** vs **verifies outputs at checkpoints** |
| Transparency vs explainability | Open about **how the system works** vs can explain **why this output** |
| Supervised vs unsupervised | **Labels** vs no labels |
| Pruning vs quantization | **Remove** weights vs **lower precision** of weights |
| System prompt vs system role | Trusted **policy instructions** vs the **persona/job** assigned to the model |
| Rate limit vs token limit vs input quota | **Requests per time** vs **tokens per request/window** vs **size/quantity of what can be submitted** |
| Log sanitization vs log protection | **Clean PII/secrets out of logs** vs keep logs **tamper-proof/access-controlled** |
| EU AI Act vs NIST AI RMF | **Binding law, risk tiers** vs **voluntary framework, four functions** |

## Domain 2 — controls quick reference

- **2.1 resources:** OWASP **LLM Top 10** + **ML Security Top 10** · **MIT AI Risk Repository** (searchable risk catalog) · **MITRE ATLAS** (adversarial knowledge base for AI, sibling of ATT&CK) · **CVE AI Working Group** (vulnerability identification for AI) · threat-modeling frameworks (e.g., STRIDE mapped onto AI components). Tools: Linux Foundation **ART** (Adversarial Robustness Toolbox), Microsoft **Counterfit**.
- **2.2 model controls:** model evaluation · model guardrails · prompt templates · guardrail testing and validation.
- **2.2 gateway controls:** prompt firewalls · rate limits · token limits · input quotas (**data size + quantity**) · modality limits · endpoint access controls.
- **2.3 access controls:** model access · data access · agent access (least privilege on tools!) · network/API access (segmentation, auth, VPC isolation).
- **2.4 data security:** encryption **in transit / at rest / in use** (in use = TEE/confidential computing, homomorphic encryption) · data safety: **anonymization, classification labels, redaction, masking, minimization**.
- **2.5 monitoring:** prompt monitoring (query + response) · log monitoring · **log sanitization** · **log protection** · response confidence level · rate monitoring · **AI cost monitoring (prompts, storage, response, processing)** · audits: hallucinations, accuracy, bias/fairness, access.

## Domain 3 — fast facts

- **3.1 tools:** IDE plug-ins, browser plug-ins, CLI plug-ins, chatbots, personal assistants, **MCP servers** (open protocol connecting AI apps to tools/data — watch for tool poisoning, rug-pulls, excessive tool permissions, injection via tool results).
- **3.1 use cases:** signature matching, code quality/linting, vulnerability analysis, automated pen testing, anomaly detection, pattern recognition, incident management, threat modeling, fraud detection, translation, summarization.
- **3.2 AI-enabled attacks:** deepfakes (impersonation, misinformation, disinformation), adversarial networks, reconnaissance, social engineering, obfuscation, automated data correlation, automated attack generation (vector discovery, payloads, malware, honeypot, DDoS).
- **3.3 automation:** low-code/no-code scripting, document synthesis/summarization, IR ticket management, change management (**AI-assisted approvals**, automated deployment/rollback), AI agents, CI/CD (code scanning, **SCA**, unit, regression, **model** testing, automated deploy/rollback).

## Domain 4 — fast facts

### Frameworks (apply, don't recite)

| Framework | Type | What it is |
| --- | --- | --- |
| EU AI Act | **Binding law** (EU) | Risk tiers: **unacceptable (banned) / high (strict obligations: risk mgmt, logging, human oversight) / limited (transparency) / minimal**; phased application from 2024; GPAI obligations |
| NIST AI RMF | **Voluntary framework** (US) | Four functions: **GOVERN · MAP · MEASURE · MANAGE** |
| ISO/IEC 42001 | Voluntary, **certifiable standard** | AI **management system** (AI-governance ISO for organizations) |
| ISO/IEC 23894 | Voluntary guidance | AI **risk management** guidance |
| OECD AI Principles | Intergovernmental **principles** (2019, updated 2024) | Values-based, not law |

- Corporate policies: **sanctioned vs unsanctioned** tools · **private vs public models** (control vs convenience) · sensitive data governance · third-party compliance evaluations (vendor audits) · **data sovereignty** (data residency + local law).

### Responsible AI principles (4.2) — the nine

Fairness · Reliability and safety · Transparency · Privacy and security · Explainability · Inclusiveness · Accountability · Consistency · Awareness training.

### The ten AI roles (4.1)

Data engineer (pipelines/data) → Data scientist (analysis/modeling) → ML engineer (builds/trains) → MLOps engineer (deploys/operates) → Platform engineer (infra) → AI architect (system design) → **AI security architect** (security design) → **AI governance engineer** (policy implementation) → **AI risk analyst** (risk assessment) → **AI auditor** (independent verification) · plus **AI Center of Excellence** (central expertise/standards/review).

### 4.2 risks

Introduction of bias · accidental data leakage · reputational loss · accuracy/performance of the model · IP-related risks · autonomous systems · **shadow AI** (unsanctioned employee AI use).
