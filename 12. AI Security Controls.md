# 12. AI Security Controls

> [!info] Exam alignment
> **Domain:** 2.0 — Securing AI Systems (40%)
> **Objectives:** 2.1 (all); 2.2 (model controls; guardrail testing and validation) — gateway controls continue in [[13. AI Access Controls|Module 13]]
> **Source notes:** `../12. AI Security Controls/` (4 files)

## Overview

Domain 2.0 is the heaviest domain on the SecAI+ exam (40% of scored content), and this module opens it with the two halves of a security engineer's job: identifying AI-specific threats with established resources (objective 2.1) and implementing model-side security controls against them (objective 2.2). Beta-exam feedback says questions are scenario-based and test applied decision-making, so expect to pick the correct threat-modeling resource for a described system, choose the correct guardrail for a stated requirement, and validate that guardrails still work after a change. This module consolidates the course notes on model risk assessment, model guardrails, prompt templates, and guardrail testing and validation, and adds full coverage of the objective 2.1 threat-modeling resources (OWASP lists, MIT AI Risk Repository, MITRE ATLAS, CVE AI Working Group, threat-modeling frameworks), which the notes barely touch. Master the "which resource answers which question" mappings — they are high-probability exam material.

## AI Threat-Modeling Resources (Objective 2.1)

Objective 2.1 reads: "Given a scenario, use AI threat-modeling resources." The exam names five resource families plus general threat-modeling frameworks. The tested skill is matching the right resource to the threat-modeling need.

| Resource | Best used for |
| --- | --- |
| OWASP Top 10 for LLM Applications | Threat modeling an application built on an LLM (chatbot, agent, RAG app) |
| OWASP ML Security Top 10 | Threat modeling classic ML systems and pipelines (classifiers, vision, fraud, recommendation) |
| MIT AI Risk Repository | Building or cross-checking a comprehensive AI risk register from documented risks |
| MITRE ATLAS | Mapping the tactics and techniques a real adversary would use against an AI system |
| CVE AI Working Group | Standardized identification and disclosure of AI-related vulnerabilities through CVE |
| Threat-modeling frameworks (STRIDE, DREAD, PASTA, LINDDUN) | Structuring and rating the threats you enumerate |

### OWASP Top 10 for LLM Applications (2025)

The community-maintained list of the most critical security risks for applications built on LLMs. The current (2025) version:

| Item | Risk | One-line summary |
| --- | --- | --- |
| LLM01 | Prompt Injection | Attacker-supplied instructions (direct or via retrieved content) override the system's intended behavior |
| LLM02 | Sensitive Information Disclosure | Model or application leaks PII, secrets, or proprietary data |
| LLM03 | Supply Chain | Vulnerable or poisoned third-party models, datasets, plugins, and dependencies |
| LLM04 | Data and Model Poisoning | Corrupting training or fine-tuning data or model artifacts to plant malicious behavior or backdoors |
| LLM05 | Improper Output Handling | Downstream systems trust LLM output unsafely, enabling XSS, command execution, SSRF, or privilege escalation |
| LLM06 | Excessive Agency | Too much autonomy, functionality, or permission for the agent's intended purpose |
| LLM07 | System Prompt Leakage | Secrets, PII, or business logic embedded in the system prompt leak to users |
| LLM08 | Vector and Embedding Weaknesses | RAG/vector-store risks: unauthorized retrieval, cross-tenant leakage, poisoned embeddings |
| LLM09 | Misinformation | Confidently produced false output (hallucination) that downstream users or systems rely on |
| LLM10 | Unbounded Consumption | Runaway requests or compute causing DoS, resource exhaustion, cost blowout, or model mining |

- Notable 2025 changes from the 2023–24 edition: System Prompt Leakage and Vector and Embedding Weaknesses became standalone categories; "Model Denial of Service" was broadened into Unbounded Consumption; "Insecure Output Handling" was renamed Improper Output Handling.
- The exam is far more likely to test recognizing the risk theme in a scenario than the exact item number — but knowing LLM01–LLM10 in order is cheap insurance.

Integration and Operational Attacks|Module 11]] (LLM05, LLM06), [[05. RAG|Module 05]] (LLM08), [[10. Model Extraction and Information Leakage Attacks|Module 10]] (LLM02, LLM07), [[13. AI Access Controls|Module 13]] (LLM10 controls).

### OWASP ML Security Top 10

Where the LLM list covers LLM applications, the ML Security Top 10 covers attacks on machine-learning systems themselves — the models, pipelines, and infrastructure of classic ML. The published list (2023 edition, maintained as a living draft):

| Item | Theme | One-line summary |
| --- | --- | --- |
| ML01 | Input Manipulation Attack | Adversarial examples/evasion — crafted inputs that mislead the model at inference |
| ML02 | Data Poisoning Attack | Corrupting training data so the learned model is wrong or backdoored |
| ML03 | Model Inversion Attack | Reconstructing sensitive training data or features from model outputs |
| ML04 | Membership Inference Attack | Determining whether a specific record was in the training set |
| ML05 | Model Theft | Stealing the model — its weights, architecture, or behavior |
| ML06 | AI Supply Chain Attacks | Compromised libraries, datasets, pre-trained models, or ML platforms |
| ML07 | Transfer Learning Attack | A poisoned or compromised pre-trained model carrying its backdoor into fine-tuned systems |
| ML08 | Model Skewing | Manipulating feedback or continuously collected data so a deployed model's behavior skews over time |
| ML09 | Output Integrity Attack | Tampering with model outputs (e.g., in transit) so downstream consumers act on altered results |
| ML10 | Model Poisoning | Malicious manipulation of the model artifact itself, distinct from data poisoning |

- The OWASP project flags this list as a frequently modified draft — recognize the themes and which list (LLM vs ML) a risk belongs to, rather than memorizing numbers.
- Pair with [[08. Data and Training Attacks|Module 08]] and [[10. Model Extraction and Information Leakage Attacks|Module 10]] for attack detail.

### MIT AI Risk Repository

- A living, searchable database of documented AI risks maintained by the MIT AI Risk Initiative (part of MIT FutureTech); launched in 2024 with 777 risks drawn from 43 published frameworks and reports, and since grown past 1,700 risks from 65 frameworks.
- Its purpose in threat modeling: comprehensiveness. When you build an AI risk register, search the catalog so you do not overlook documented risk classes outside your first instincts (it spans far more than security).
- Risks are organized with two taxonomies:
  - **Causal taxonomy** — root cause along three dimensions: responsible entity (human vs AI system), intentionality (intentional vs unintentional), and timing (pre-deployment vs post-deployment).
  - **Domain taxonomy** — seven domains: discrimination and toxicity; privacy and security; misinformation; malicious actors and misuse; human–computer interaction; socioeconomic and environmental impacts; and AI system safety and limitations (23 subdomains).
- Classic distractor: the MIT AI Risk Repository is a *database of risks*; the NIST AI RMF (below) is a *framework of functions for managing* risk. "Search a catalog of documented risks" → MIT repository; "apply a management framework" → NIST AI RMF.

### MITRE ATLAS

- ATLAS (Adversarial Threat Landscape for Artificial-Intelligence Systems) is a knowledge base of adversary tactics, techniques, and real-world case studies for attacks on AI/ML systems, structured the same way as MITRE ATT&CK.
- It is a companion to ATT&CK, not a replacement: ATT&CK documents adversary behavior against traditional enterprise IT, and ATLAS extends that model to attacks on AI systems and ML supply chains.
- Representative ATLAS techniques (know the names, not the IDs): ML model poisoning, poisoning training data, ML model stealing, adversarial ML (evasion), exfiltration via ML API, and harvesting private ML model information.
- ATLAS case studies document real-world attacks, which makes it useful for grounding a threat model in observed adversary behavior.

| Question in the scenario | Correct resource |
| --- | --- |
| How would an adversary attack our ML training pipeline? | MITRE ATLAS |
| How would an adversary attack our enterprise network? | MITRE ATT&CK |
| What are the top risks in our LLM-powered chat app? | OWASP Top 10 for LLM Applications |
| What are the top risks in our fraud-detection ML model? | OWASP ML Security Top 10 |
| Are we missing any documented AI risk categories in our register? | MIT AI Risk Repository |
| How do we track an AI component flaw as a standard vulnerability? | CVE (via the CVE AI Working Group's work) |

### CVE Program AI Working Group

- CVE (Common Vulnerabilities and Exposures) is the standard dictionary of identifiers for publicly disclosed vulnerabilities.
- The CVE Artificial Intelligence Working Group (CVEAI WG) — chartered in 2024 (charter v1.1, September 2024) — extends the CVE Program's work to AI: researching how vulnerabilities in AI systems and components are identified, described, and published as CVEs, and closing gaps in the CNA (CVE Numbering Authority) process for AI-related flaws.
- Why it matters for the exam: it means AI components (models, runtimes, frameworks, tooling) are brought into the same coordinated vulnerability identification and disclosure ecosystem as any other software.
- Match in a scenario: "standardized identification and coordinated disclosure of AI vulnerabilities" → CVE AI Working Group.

### Threat-Modeling Frameworks Applied to AI

The objective simply says "threat-modeling frameworks" — apply the classic frameworks with AI components in scope.

STRIDE, mapped to AI systems:

| STRIDE | AI manifestation | Example control |
| --- | --- | --- |
| Spoofing | Impersonating users or services to the AI stack; deepfaked identity or voice | Strong authentication, mTLS |
| Tampering | Modifying training data, model weights, system prompts, RAG documents, or prompts in transit | Integrity controls, signed artifacts, versioning |
| Repudiation | Agent actions or model decisions that cannot be attributed | Audit logging |
| Information disclosure | System prompt leakage, training data leakage (inversion, membership inference), PII in outputs | Output filtering, DLP, access controls |
| Denial of service | Unbounded consumption, context flooding, resource exhaustion | Rate/token limits (see [[13. AI Access Controls|Module 13]]) |
| Elevation of privilege | Prompt injection escalating an agent beyond its intended permissions | Least privilege, allowlists, human approval |

- **DREAD** — a rating model applied to each identified threat: Damage, Reproducibility, Exploitability, Affected users, Discoverability.
- **PASTA** — Process for Attack Simulation and Threat Analysis: a risk-centric, seven-stage methodology that ties attack simulation to business objectives.
- **LINDDUN** — privacy-focused threat modeling (Linkability, Identifiability, Non-repudiation, Detectability, Disclosure of information, Unawareness, Non-compliance); a natural fit for AI data-privacy risks.
- STRIDE answers "what can go wrong"; DREAD answers "how bad is it"; PASTA answers "what should we model, in what order, tied to what matters."

## Model Risk Assessment and Model Evaluation

- Model risk assessment is the process of evaluating how an AI system performs under both normal and challenging conditions. Every model should be tested before deployment so it behaves safely, securely, and ethically.
- It matters most for LLMs that interact directly with users or make sensitive decisions.
- Security-focused evaluation looks beyond accuracy: it examines how the model responds to manipulation, bias, and compliance requirements.
- Testers deliberately try to uncover vulnerabilities before attackers can, probing edge cases that push the model to its limits — verifying it performs core tasks reliably while adhering to established guidelines.
- Tooling from the notes:
  - **Adversarial Robustness Toolbox (ART)** — Linux Foundation library for adversarial ML; detects adversarial examples and data-poisoning exposure.
  - **Counterfit** — Microsoft's command-line tool that automates security risk assessment of ML models by orchestrating adversarial attacks.
- Assessment findings feed compensating controls and mitigation strategies — this is the bridge from objective 2.1 (identify threats) to 2.2 (implement controls).
- The NIST AI Risk Management Framework (AI RMF) supports assessment: identify and document a model's capabilities, limitations, and risks — strengths and weaknesses — before deployment. Its four core functions: **GOVERN** (roles, accountability, risk tolerance), **MAP** (context and risk identification), **MEASURE** (evaluation, testing, monitoring), and **MANAGE** (prioritized treatment of risks). A Generative AI Profile supplements it with genAI-specific actions. See [[20. AI GRC|Module 20]].
- **Model evaluation as a control** (objective 2.2 "model controls"): treat evaluation as a gate, not a paperwork step.
  - Pre-deployment gate: no model goes to production without passing functional, safety, adversarial-robustness, and bias evaluation.
  - Continuous evaluation: models drift and users probe them; re-evaluate in operation on a schedule and after every change.
  - Evaluate third-party and vendor models before use — an unexamined model is an inherited risk.
  - Evaluate against both task metrics (accuracy) and security metrics (evasion resistance, extraction resistance) — the notes' key point that security evaluation goes beyond accuracy.
- Lifecycle placement of evaluation: [[06. Security in the AI Lifecycle|Module 06]].
- Terminology nuance the exam may probe: *model evaluation* is the measurement activity; *model risk assessment* is the broader judgment of what could go wrong and how badly. Evaluation feeds assessment.

## Model Guardrails

- Model guardrails are the technical and policy safeguards that keep an AI system operating safely: they hold the model within acceptable limits, prevent harmful outputs, and enforce security and ethical guidelines.
- They protect users, data, and organizations from unintended or unsafe AI behavior, and they act at three points: on input (before the model), on model behavior (training and policy), and on output (before the user sees the response).

### Guardrail Techniques

| Technique | How it works | Cautions |
| --- | --- | --- |
| Rule-based filtering | Deterministic keyword/pattern blocks for forbidden topics and PII | Fast and auditable, but brittle — obfuscation bypasses it |
| Content moderation | A secondary classifier model scores input/output for hate speech, self-harm, explicit material | Catches context that rules miss, but requires tuning |
| Response tuning and refusal | The model itself is trained or system-prompted to refuse specific prompts | Needs testing to confirm refusals hold under pressure |
| Constrained output formatting | Forces structured output (schemas) compatible with downstream systems | Prevents the model injecting unintended or unsafe content into structured outputs |
| Topic restrictions and grounding | Restricts the model to allowed topics and grounds answers in approved sources/knowledge | Grounding in curated content reduces misinformation — see [[05. RAG|Module 05]] |

- Guardrails are difficult to balance: overly strict guardrails block legitimate use cases, and poorly tuned moderation systems either overreact or fail to catch violations. Track both failure directions — bypass rate (too weak) and false-positive rate (too strict).
- Guardrails vs prompt templates vs prompt firewalls (likely compare-and-contrast):
  - **Model guardrails** — the broad category: input/output filters, content policies, behavior controls.
  - **Prompt templates** — a model-side guardrail technique that structures interactions (below).
  - **Prompt firewall** — a gateway-side inspection/filtering service in front of the model; covered in [[13. AI Access Controls|Module 13]].

### Prompt Templates as a Guardrail

- Prompt templates act like reusable scripts that tell the model what role to take, what tone to use, and what limits to follow. They wrap input into a structured format so the AI stays on task and produces consistent, safe responses.
- A standardized prompt contains predefined instructions with one or more open slots for user input; this standardizes interactions across teams and users.
- As a security control against prompt injection: the model is constrained to process only user input that fits within a specific slot — user input is treated as data, never as instructions, so a user's attempt to insert hidden instructions that override system rules is contained.
- Delimiters (clearly marked boundaries around the user-input slot) mark where instructions end and data begins, reinforcing the instructions-vs-data separation.
- When combined with output filters such as content moderation, templates form a strong first line of defense.
- Prompt engineering background: [[03. Prompt Engineering|Module 03]]. Attack variations they must resist: [[09. Prompt and Input Manipulation Attacks|Module 09]].

## Guardrail Testing and Validation

- Guardrail testing and validation is essential for keeping AI systems safe, reliable, and compliant. Guardrails must be validated because attack techniques unique to AI constantly evolve — prompt injection, obfuscated inputs, and prompt-based filter bypasses.
- Regular testing confirms guardrails still perform as intended and that any model updates or retraining do not introduce new vulnerabilities.

### Testing Techniques (from the notes)

- **Jailbreak testing** — deliberately attempt prompts that bypass safety rules: roleplay framing, encoding (base64, character substitution), multi-turn manipulation, and template-slot escapes.
- **Output validation** — verify responses against policy before they reach users. Use canary string identification: embed a unique marker string in the system prompt or sensitive data; if the canary appears in model output or logs, leakage is confirmed.
- **Log monitoring** — watch for bypass attempts, anomalous usage, and spikes in refusals; see [[15. AI Monitoring and Auditing|Module 15]].
- **Human feedback** — users and reviewers report guardrail failures (both misses and over-blocking); feed the reports back into tuning.

### Expanding on the Notes

- **Red-teaming guardrails** — authorized adversarial testing of the whole AI system, guardrails included. For ML models, reuse the assessment tooling from earlier in this module: ART and Counterfit automate evasion and poisoning tests; jailbreak prompt suites do the equivalent for LLMs.
- **Regression testing of guardrails** — treat the guardrail test suite as a versioned asset and re-run it after every model update, fine-tune, guardrail configuration change, or data-pipeline change (new sources or preprocessing — see [[04. Data Processing|Module 04]]). A guardrail that passed last quarter's model can silently fail on the new one.
- **Measure what matters** — bypass rate (guardrail too weak), false-positive/over-blocking rate (guardrail too strict), and latency overhead (guardrails that make the product unusable).
- Lifecycle view of where testing fits: [[06. Security in the AI Lifecycle|Module 06]].

## Exam Focus

- Objective 2.1 verbatim: "Given a scenario, use AI threat-modeling resources." Objective 2.2 verbatim: "Given a set of requirements, implement security controls for AI systems" (this module: model evaluation; model guardrails, including prompt templates; guardrail testing and validation).
- Compare-and-contrast pairs to master: OWASP LLM Top 10 vs OWASP ML Security Top 10 (LLM applications vs ML systems); MITRE ATT&CK vs ATLAS (enterprise IT vs AI systems); MIT AI Risk Repository vs NIST AI RMF (database of risks vs framework of functions); guardrails vs prompt templates vs prompt firewalls (behavior policy vs structured slots vs gateway filtering); model evaluation vs model risk assessment (measurement vs judgment); data poisoning vs model poisoning (ML02 vs ML10 theme).
- Classic distractor confusions: picking ATT&CK when the scenario describes an attack on an ML pipeline (should be ATLAS); picking the MIT AI Risk Repository when asked for a management framework (should be NIST AI RMF); calling a WAF a prompt firewall (a WAF filters web-application HTTP attacks, not LLM prompts — see [[13. AI Access Controls|Module 13]]); assuming guardrails are "set and forget" (they need continuous testing and regression); confusing Unbounded Consumption (LLM10) with a pure network DoS.
- Likely scenario shapes: "An organization is building a customer-facing chatbot — which resource identifies its top risks?" (OWASP LLM Top 10); "Which resource maps observed adversary behavior against AI systems?" (MITRE ATLAS); "Given requirements to block PII leakage and hate speech, which controls?" (rule-based filtering + content moderation + output validation); "After retraining a model, users report the assistant discussing forbidden topics — what failed?" (guardrail regression testing); "How do you prove system-prompt data leaked?" (canary string).
- Remember Domain 2.0 is 40% of the exam — the heaviest domain — and this module supplies the resource-selection questions that beta testers reported as heavily scenario-based.

## Self-Check

1. A team is compiling an AI risk register for a new HR screening tool and wants to check for documented AI risk categories beyond security (discrimination, privacy, misinformation). Which resource do they search, and what distinguishes it from the NIST AI RMF?
2. An organization wants a prioritized list of the most critical risks for its new customer-facing chatbot built on an LLM. Which resource fits best?
3. A threat model needs to describe how an adversary might poison training data, steal a model, and evade a deployed classifier. Which knowledge base provides these AI-specific tactics and techniques, and how does it relate to MITRE ATT&CK?
4. A security team discovers its fraud-detection model was fine-tuned from a poisoned pre-trained model. Which OWASP ML Security Top 10 theme is this, and which LLM Top 10 item covers the same underlying idea?
5. Requirements state: block PII from appearing in responses, block hate speech in inputs, and never emit unvalidated free-form JSON to the ordering system. Which three guardrail techniques satisfy these requirements?
6. After a model was retrained last week, users report the assistant discussing prohibited topics that guardrails previously blocked. What process failed, and what should have been done?
7. How can a team prove that data embedded in a system prompt is leaking into user-visible output, and which guardrail testing technique does this belong to?
8. A developer wants user-supplied text treated strictly as data so embedded instructions cannot override the application's rules. Which model guardrail technique implements this, and what marks the boundary?

### Answers

1. The MIT AI Risk Repository — a living database of documented AI risks (with causal and seven-domain taxonomies) used to cross-check registers for coverage. The NIST AI RMF is a framework of management functions (GOVERN, MAP, MEASURE, MANAGE) for handling risk, not a searchable catalog of risks.
2. The OWASP Top 10 for LLM Applications — its ten items (prompt injection, sensitive information disclosure, excessive agency, unbounded consumption, and so on) are the prioritized risks for LLM applications specifically.
3. MITRE ATLAS — a knowledge base of adversary tactics, techniques, and real-world case studies for attacks on AI/ML systems. It is a companion to ATT&CK: ATT&CK covers traditional enterprise IT attacks; ATLAS extends the same style to AI systems.
4. Transfer learning attack (ML07) — a poisoned pre-trained model carries its backdoor into fine-tuned systems. The same underlying idea appears in the LLM list as Data and Model Poisoning (LLM04), which merges training-data and model-artifact corruption.
5. Rule-based filtering (deterministic PII blocks), content moderation (secondary classifier for hate speech), and constrained output formatting (schema-bound output for the ordering system). Output validation would additionally check responses before delivery.
6. Guardrail regression testing failed — the guardrail test suite was not re-run after retraining. The suite should be a versioned asset re-executed after every model update, fine-tune, guardrail change, or data-pipeline change.
7. Canary string identification, part of output validation: embed a unique marker in the system prompt or sensitive data; if the canary surfaces in model output or logs, leakage is confirmed.
8. Prompt templates — predefined instructions with open slots that confine user input to a slot where it is treated as data, not instructions. Delimiters mark the boundary between the application's instructions and user-supplied data; combined with output filters they form a strong first line of defense.
