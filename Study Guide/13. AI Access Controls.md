# 13. AI Access Controls

> [!info] Exam alignment
> **Domain:** 2.0 — Securing AI Systems (40%)
> **Objectives:** 2.2 (gateway controls); 2.3 (all) — model controls and guardrails are in [[12. AI Security Controls|Module 12]]
> **Source notes:** `../13. AI Access Controls/` (6 files)

## Overview

Domain 2.0 is the heaviest domain on the SecAI+ exam (40% of scored content), and this module completes objective 2.2 with the *gateway* controls — prompt firewalls, rate limits, token limits, input quotas, modality limits, and endpoint access controls — plus all of objective 2.3, the access controls across the model, data, agent, and network/API layers. The beta exam is scenario-based, so the highest-value skills here are applied decision-making: given a symptom (cost blowout, denial of service, abuse, data leakage), pick the correct limit or access control; and given a set of requirements, apply least privilege to the right layer. Model-side guardrails, evaluation, and threat-modeling resources are covered in [[12. AI Security Controls|Module 12]] — know which controls belong at the gateway and which belong to the model itself, a likely compare-and-contrast item.

## Gateway Controls (Objective 2.2)

Gateway controls sit between the user or application and the model, filtering what gets in, capping how much gets in, and restricting which endpoints and input modalities are reachable at all. They complement model controls: guardrails change model behavior; gateway controls police the traffic around it.

### Prompt Firewalls

- A prompt firewall inspects, filters, and sanitizes user requests before they reach the model, sitting between the user/application and the model — acting like a web application firewall (WAF) for LLM traffic.
- Primary purpose: protection against prompt injection. It also helps prevent sensitive data leaks and policy violations.
- Some prompt firewalls also review model output before it reaches the end user, blocking content that violates company policy. They are also referred to as an AI/LLM guardrail and can inspect both inbound prompts and outbound responses — bidirectional filtering.
- The most effective prompt firewalls combine static rules (deterministic blocks) with intelligent detection — machine learning models that recognize more subtle or contextual risks.
- No firewall can stop every attack, but one significantly reduces the risk of sensitive data exposure and model jailbreaking. Layer it with model guardrails ([[12. AI Security Controls|Module 12]]) rather than treating it as sufficient alone.
- Placement: a prompt firewall is deployed as an inline proxy, an API-gateway plugin, or a sidecar in front of the model. What matters for exam scenarios is the pattern — filter inbound *before* the model, validate outbound *before* the user.
- What it inspects on the way in: instruction-like phrasing and role-override attempts (injection patterns), jailbreak heuristics, PII and secrets in the prompt (stops sensitive data leaving), topic boundaries, and encoding tricks (base64, unicode homoglyphs) that try to slip past static rules.
- What it inspects on the way out: policy-violating content, PII/secrets in responses, and canary strings planted to detect leakage (see [[12. AI Security Controls|Module 12]]).
- WAF vs prompt firewall (classic distractor — likely exam item):

| Filter | Traffic it inspects | Attacks it stops |
| --- | --- | --- |
| WAF | HTTP requests/responses to web applications | Traditional web exploits: SQL injection, XSS, SSRF patterns |
| Prompt firewall | Natural-language prompts and model input/output | Prompt injection, jailbreaks, policy violations, sensitive data exfiltration |

  Real deployments layer both in front of an LLM application — they are complements, not alternatives.
- Distinguish from model guardrails: a prompt firewall is a gateway service that polices traffic to and from the model; guardrails (filters, moderation, refusal training, templates) shape model behavior itself — see [[12. AI Security Controls|Module 12]].
- Attack background: [[09. Prompt and Input Manipulation Attacks|Module 09]].

### Rate Limits, Token Limits, and Input Quotas

- Limits and quotas are simple yet effective: they control how often a user or system can interact with a model and how much data each interaction can consume, capping the damage a malicious or careless user can do.
- Rate limiting is the foundation: it caps the number of requests per user per time period. It prevents DoS, spam, and general model abuse; ensures all users have fair access; and deters brute force, jailbreak, and model extraction attempts.
- AI workloads are more demanding than traditional computing, so standard request-count rate limiting is insufficient — requests are not equal. A one-line question and a 200-page document upload are both "one request," so AI systems use token-based rate limiting as well.
- Input limits (context window limits) cap how much can enter the model, preventing excessive text prompts or large file imports.
- Output limits restrict how long a response can be, reducing resources consumed and limiting data exposure through lengthy answers. If a longer answer is required, output can be split into multiple separate responses.
- Concurrent request limits cap how many queries a user can run at one time, preventing DoS.
- The mandatory comparison — match the control to the symptom:

| Control | What it caps | Unit and window | Symptom it addresses |
| --- | --- | --- | --- |
| Rate limit | Number of requests per user/service | Requests per time period (per minute/hour) | DoS, spam, scraping, brute-force and extraction attempts — request floods |
| Token limit | Tokens consumed per request or per window | Input/output tokens per request or per time window | Cost blowout and resource exhaustion from long prompts or long generations |
| Input quota — data size | Size of any single submission | Bytes/MB per file, prompt character or token count, image dimensions | Huge prompt stuffing and large file import abuse |
| Input quota — quantity | Number of items submitted | Files, documents, or records per request or per period | Bulk upload abuse (e.g., flooding a RAG ingestion endpoint) |

- Exam shape: "requests per minute exploding" → rate limits; "each request is enormous / long generations driving cost" → token limits (and output limits); "users uploading massive files" → input quotas (data size); "hundreds of documents per upload" → input quotas (quantity).
- Worked example — a support-chatbot gateway applies all four caps at once, each aimed at a distinct abuse path:
  - 20 requests per minute per user → request floods (rate limit).
  - 4,000 input tokens per request → context stuffing (token limit, input side).
  - One attachment, max 5 MB → oversized uploads (input quota, data size).
  - 2,000 output tokens per response → generation cost and verbose leakage (output limit).
- Quotas apply per subject: per user, per API key, per application, or per model endpoint — the exam may test *who or what* the cap attaches to, not just that a cap exists.
- Limits as compensating controls: they do not fix a vulnerability, they cap the blast radius — cost, DoS impact, extraction speed, and careless-user damage (the notes' core point: limits "limit potential damage caused by a malicious or careless user").
- Rate limiting also deters model extraction: extraction requires many high-volume queries, which a rate/token limit makes slow, expensive, and noisy — see [[10. Model Extraction and Information Leakage Attacks|Module 10]].

### Modality Limits

- Modality limits restrict the types of inputs and outputs the model can handle — text, images, audio, file attachments.
- Every additional modality increases the attack surface: images and audio can carry hidden injection payloads (text hidden in an image or a voice instruction), file attachments bring malware and parsing risk, and generative image/audio output enables deepfake creation.
- Disable unused modalities per use case and per endpoint: a text-only internal summarization endpoint should reject image uploads outright.
- Limits apply to output modalities too: an endpoint approved for text answers should not generate images or audio, even if the underlying model can.
- Enforce at the endpoint/gateway, not only in the application UI — a disabled button in the front end is not a control; a rejection at the model endpoint is.
- Compare with the data-level view of input validation: [[04. Data Processing|Module 04]].

### Endpoint Access Controls

- Endpoint access controls govern who and what can reach which model endpoints — chat/completions, embeddings, fine-tuning, batch, and admin/management interfaces.
- Apply least privilege per endpoint: ordinary users may invoke inference but not fine-tune; only the ML pipeline service should reach training and fine-tuning endpoints; admin/management planes should be separated from the data plane and never exposed to general users.
- API gateways provide the natural enforcement point: authentication, authorization, routing, and usage limits per endpoint (tie-in with rate limits above).
- Give each application its own scoped credential to a specific endpoint — not a shared master key reused across services; rotation and revocation then affect one consumer, not the fleet.
- Expose one endpoint per model version and pin consumers to approved versions; block access to deprecated or staged models still under evaluation.
- Endpoint access controls are the gateway-side enforcement of the model access rules in objective 2.3 (next section).

### Enforcing and Measuring Gateway Controls

- Enforcement point: nearly all gateway controls are configured at the API/LLM gateway — the same chokepoint that authenticates clients, so policy lives in one place and applies to every model behind it.
- Tiered quotas: limits differ by consumer class — anonymous users get the tightest caps, authenticated internal users more, and pipeline service accounts exact quotas matched to their workload.
- Alert on limit events, not just enforce them: sudden spikes in rate-limit hits, quota breaches, and modality rejections are attack signals (extraction, DoS, probing) that feed the monitoring loop — see [[15. AI Monitoring and Auditing|Module 15]].
- Governance: review quotas when use cases change; a limit sized for one workload becomes a bottleneck — or a blind spot — for the next one.

## Model Access Controls (Objective 2.3)

- Model access controls determine who has access to a model, what they can do to it, and how they access it — preventing unauthorized use and theft of the model itself.
- Authentication is the first line of defense: all users should have valid credentials appropriate to their level of access, integrated with enterprise authentication services (e.g., SSO, Active Directory). External access can be provisioned through an API token or a similar scoped credential.
- RBAC (role-based access control) determines permissions based on the authenticated user's role; ABAC (attribute-based access control) applies additional conditions on varying factors such as device type, time of day, and user location.
- API gateways and access management systems enforce model access centrally.
- Protect the model's weights, configurations, and supporting files: encrypt at rest and apply strict access control — see [[14. Encryption and Data Safety|Module 14]] and the model theft/extraction risks in [[10. Model Extraction and Information Leakage Attacks|Module 10]].
- Monitor for suspicious access and data exfiltration attempts, and for general anomalous activity — see [[15. AI Monitoring and Auditing|Module 15]].
- Set usage quotas or rate limits on model consumers (gateway enforcement of these access decisions).
- Expand beyond the notes — separate the model lifecycle roles on registries and endpoints: consume/inference, fine-tune, publish/approve, deploy, and quarantine/rollback. A data scientist who may fine-tune does not necessarily need production deploy rights; the registry, not just the API, needs RBAC.
- Two-person rule for high-impact actions: production deployment and external sharing of model artifacts should require approval by a second authorized person.
- Provenance and admission controls: only approved, signed model artifacts may enter the registry — model cards and lineage record who introduced each model and from where (AI supply-chain control; see [[08. Data and Training Attacks|Module 08]] and [[11. Integration and Operational Attacks|Module 11]]).
- Never expose model weights through general inference APIs: extraction becomes possible when the same endpoint that answers prompts also serves weights or configurations — see [[10. Model Extraction and Information Leakage Attacks|Module 10]].
- Monitor the model access logs for anomalies the rules cannot prevent: off-hours access, bulk reads, permission-change events — see [[15. AI Monitoring and Auditing|Module 15]].

## Data Access Controls

- Sensitive AI system data includes training data — personal information, proprietary data, and internal communications.
- Restrict training-data access to just the authorized ML team members or the automated pipelines used for model development.
- When sharing data externally for fine-tuning, use encryption, NDAs, and privacy-preserving techniques such as anonymization to reduce exposure — see [[14. Encryption and Data Safety|Module 14]].
- Inference and output data need strong access control too: prompts and responses can reveal sensitive details, and if interactions are logged for analysis, protect those logs as part of access control.
- Underlying data sources: many AI systems return data from internal systems, APIs, or document repositories. Those sources should still be subject to an access control check even when the request comes from an AI model.
  - The AI should authenticate using the identity of the requesting user account, or a restricted service account — never a broad privileged identity.
  - Permissions should be segmented, and responses should only return output the requesting user is authorized to see.
  - For RAG, this means document-level access control must survive retrieval: the index should carry the source's permission tags, and query-time filtering should drop chunks the requesting user cannot see. The classic failure is building the vector index with a privileged service account and then serving its contents to every user — cross-tenant/cross-role leakage. See [[05. RAG|Module 05]].
- DLP tools monitor and protect data as it moves through the AI system (prompt and response inspection, sensitive-data egress).
- Let data classification drive access: label training corpora by sensitivity — the more sensitive the corpus, the fewer identities that hold access to it.
- Least privilege for pipeline service accounts too: training pipelines get short-lived, narrowly scoped credentials with just-in-time elevation for the training job, not standing access to the data lake.
- Protect evaluation/test data as well as training data: leaked test sets reveal exactly what the model is measured on — see [[04. Data Processing|Module 04]].
- Prompt/response logs are sensitive data: restrict access, encrypt at rest, and set retention periods — see [[14. Encryption and Data Safety|Module 14]] and [[15. AI Monitoring and Auditing|Module 15]].
- Attack background for what these controls stop: [[08. Data and Training Attacks|Module 08]] (poisoning needs training-data write access) and [[10. Model Extraction and Information Leakage Attacks|Module 10]] (inference-time leakage).

## Agent Access Controls

- An agent can be manipulated into performing unwanted actions — via prompt injection into its instructions, tool results, or retrieved content (see [[11. Integration and Operational Attacks|Module 11]] and [[09. Prompt and Input Manipulation Attacks|Module 09]]). Controls limit what a compromised agent can actually do.
- Rate limiting and monitoring: cap how often an agent can act within a specific timeframe. Combining these two controls provides adaptive defense against agent compromise — unusual action volume is both throttled and flagged.
- Principle of least privilege: treat agents like users — they should only have access to the minimum permissions required to complete their task.
  - Avoid direct connections between agents and critical systems; route sensitive actions through an intermediary (gateway, queue, or approval step).
  - Use scoped, short-lived credentials per agent rather than long-lived broad service accounts, and allowlist the specific tools, commands, domains, or actions an agent may use.
- Tool allowlists: enumerate the specific tools, actions, commands, and destination URLs an agent may use, deny by default — never grant generic web browsing, shell, or database access where a narrow capability suffices.
- Budget and session limits: cap tokens, tool calls, and cost per task/session, and limit conversation turns — multi-turn manipulation and runaway loops are bounded by construction.
- Sandboxing: agents that generate or execute code should run in an isolated environment with no standing access to production systems.
- Review and approval mechanisms: require an engineer (or other human authority) to approve code changes or other potentially risky actions — human-in-the-loop for high-impact operations (payments, deletions, infrastructure changes). Tier actions by impact: reads run automatically; writes pause for approval; destructive or financial actions require a named human authority.
- This is the countermeasure to excessive agency (OWASP LLM06): excessive permissions make injection catastrophic; least privilege plus approval gates make it survivable — see [[12. AI Security Controls|Module 12]].

## Network and API Access Controls

- Controlling network/API access ensures only legitimate requests reach the model. Core controls:
  - Enforce authentication, authorization, and usage limits at the network and API layer.
  - Network isolation: AI models should not be directly exposed to the public internet. Provide access through private networks or cloud subnets reachable only via secure gateways. IP allowlisting, VPCs (virtual private clouds), and gateways restrict which systems or users can connect.
  - Secure communication protocols: encrypt data in transit with HTTPS/TLS; use mutual TLS (mTLS) for service-to-service traffic where both sides authenticate with certificates.
  - Throttling and circuit breakers maintain stability: throttling limits how many requests can be processed; circuit breakers automatically pause or reroute traffic if the system becomes overloaded.
  - Audit logging paired with network and API access controls enhances visibility and accountability — see [[15. AI Monitoring and Auditing|Module 15]].
- Segment the AI environments: training/development infrastructure and production inference should sit in different network zones with different credentials — a compromised training sandbox should not have a network path to production endpoints.
- Zero-trust posture: authenticate and authorize every request even inside the private network — network location alone is not authorization.
- API key hygiene where static keys remain in use: scope one key per application, rotate on a schedule, and never embed keys in client-side code or prompts; prefer OAuth flows where users act for themselves.
- Audit logging paired with network/API controls: record identity, endpoint, model version, token counts, and allow/deny decisions — visibility and accountability — see [[15. AI Monitoring and Auditing|Module 15]].
- Exam acronyms (CompTIA lists VPC, OAuth, NACL among the acronyms):
  - **VPC** — virtual private cloud: an isolated private network segment in the cloud where inference endpoints can live with no public exposure.
  - **NACL** — network access control list: subnet-level, stateless allow/deny rules filtering traffic to the subnet hosting the AI service (typically paired with host-level stateful security groups).
  - **OAuth** — open-standard delegated authorization: scoped, expiring tokens for API access. Prefer OAuth/scoped tokens over static API keys for user-facing and inter-application AI access; static API keys are bearer credentials — leaked once, valid until rotated.
  - **mTLS** — mutual TLS: both client and server present certificates, suited to gateway-to-model and service-to-service traffic.
- Also consider egress controls: restricting what the model or agent can reach outbound (external APIs, URLs) limits SSRF-style abuse and data exfiltration — see [[11. Integration and Operational Attacks|Module 11]].

## Layered Control Map (Defense in Depth)

No single control stops everything — the notes make this point for prompt firewalls, and the exam rewards layered answers. Trace a prompt-injection attempt against a RAG chatbot through the layers:

| Layer | Control (objective) | What it does with a malicious prompt |
| --- | --- | --- |
| Input acceptance | Modality limits (2.2) | Rejects disallowed file types and modalities outright |
| Gateway | Prompt firewall (2.2) | Inspects, filters, and sanitizes the prompt before it reaches the model |
| Gateway | Rate/token limits, input quotas (2.2) | Cap floods, oversized payloads, and runaway generation cost |
| Gateway | Endpoint access controls (2.2) | Authenticated, authorized clients only reach the approved endpoint |
| Model | Guardrails, prompt templates (2.2 — [[12. AI Security Controls|Module 12]]) | Confines user input to a data slot; content policies and refusal |
| Agent | Least privilege, allowlists, HITL (2.3) | Caps the blast radius if the injection succeeds |
| Data | Per-user access on underlying sources (2.3) | Retrieval returns only what the requester is authorized to see |
| Network | VPC/NACL/TLS (2.3) | Keeps the endpoint private and traffic encrypted |
| Monitoring | Log monitoring ([[15. AI Monitoring and Auditing|Module 15]]) | Surfaces bypass attempts and anomalies for guardrail tuning |

- The same map answers other exam scenarios: a model-extraction attempt is capped by rate/token limits (slow and noisy) and caught by monitoring; an unbounded-consumption incident is capped by token/output limits; a poisoned-upload attempt is stopped by input quotas and modality limits at the front door.
- Exam mindset: pick the best-fit control for the stated symptom or requirement, and when two options both "work," prefer the layered answer that also caps the blast radius.

## Exam Focus

- Objective 2.2 verbatim: "Given a set of requirements, implement security controls for AI systems" — this module's slice: prompt firewalls; rate limits; token limits; input quotas (data size; quantity); modality limits; endpoint access controls. Objective 2.3 verbatim: "Given a scenario, implement appropriate access controls for AI systems" — model access; data access; agent access; network/API access.
- Compare-and-contrast pairs to master: rate limit vs token limit vs input quota (the table above — requests per time vs tokens per request/window vs caps on submission size and quantity); RBAC vs ABAC (role vs contextual attributes such as device, time, location); prompt firewall vs WAF (LLM traffic inspection vs web-exploit filtering); API key vs OAuth token (static bearer credential vs scoped, expiring delegated authorization); gateway controls vs model controls (perimeter vs behavior); NACL vs security group (stateless subnet-level vs stateful host-level); agent treated as untrusted vs trusted principal.
- Classic distractor confusions: answering "rate limit" for a cost-blowout-from-huge-generations symptom (correct answer is token/output limits); answering "WAF" for prompt-injection filtering (correct answer is a prompt firewall); building a RAG index under a privileged service account and serving it to all users (correct design carries document-level permissions through retrieval); giving an agent a long-lived broad service account (correct answer is least-privilege scoped credentials plus approval gates); assuming encryption at rest solves model theft (access control on weights and endpoints is also required).
- Likely scenario shapes: "Given requirements (only the ML team may fine-tune; external partners may only infer) — implement access controls" (RBAC on the model registry/endpoints plus scoped API tokens); "Inference costs are spiking because users paste entire documents and request maximum-length answers" (token limits, input quotas on data size, output limits); "A file-upload chatbot also accepts audio, which the use case never needs" (modality limits); "An agent with pipeline write access was prompt-injected into approving changes" (least privilege, tool allowlists, human-in-the-loop approval); "Which resource should the AI authenticate as when it queries internal document stores?" (the requesting user's identity or a restricted service account).
- Remember these two objectives sit inside the heaviest exam domain (40%) alongside [[12. AI Security Controls|Module 12]] — expect control-selection scenarios rather than definition recall.

## Self-Check

1. A chatbot's hosting bill tripled in a month. Logs show a modest number of requests, but users are pasting entire documents into every prompt and requesting maximum-length responses. Which controls address this most directly?
2. A burst of thousands of requests per minute from a single account is degrading service for everyone. Which control applies, and which related cap targets *simultaneous* queries?
3. An organization's support chatbot is text-only by requirement, but the vendor platform has image and audio input enabled. What should change, and why?
4. A RAG assistant indexes a document repository that mixes public and HR-restricted documents. The index was built by a privileged service account, and all users can query it. What is the flaw, and what is the correct design?
5. An internal agent holds a long-lived service account with write access to the deployment pipeline. After a prompt injection through a web page it summarized, it began submitting code changes. Name three controls that would have contained this.
6. The ML platform team needs to let data scientists run experiments (fine-tuning) without letting them deploy to production, while external partners get inference-only access. Which control model implements this?
7. Security wants to ensure requests to an internal model inference endpoint are filtered for prompt injection and policy violations before reaching the model, and that responses are checked before reaching users. Which control does this, and how does it differ from the company's existing WAF?
8. A model inference service must never be reachable from the public internet. Which network controls implement this?
9. An application team needs programmatic access to the embeddings endpoint only; a data pipeline needs the fine-tuning endpoint. Both currently share one organization-wide API key with access to every model endpoint. What is the risk, and what is the better design?

### Answers

1. Token limits (per request/window) plus input quotas on data size (caps on prompt/file size) and output limits on response length. The problem is per-request volume, not request count — a rate limit alone would not fix it.
2. Rate limiting caps requests per time period; concurrent request limits cap how many queries a user runs at once. Both prevent DoS and ensure fair access; rate limits also deter brute-force, jailbreak, and model-extraction attempts.
3. Apply modality limits — disable image and audio input on the endpoint. Each additional modality increases the attack surface (hidden injection payloads in images/audio, malicious file parsing risk) and is unnecessary when the use case is text-only.
4. Document-level access control must survive retrieval: the index was built under a privileged identity so restricted content is served to any user who queries. The AI should authenticate as the requesting user (or a restricted service account), carry source permission tags into the index, and filter retrieved chunks at query time so responses only return output the requesting user is authorized to see.
5. Any three of: least privilege for the agent (treat agents like users — minimum permissions only, no direct connection to critical systems); scoped, short-lived credentials instead of a broad long-lived service account; tool/command allowlists; rate limiting and monitoring of agent actions; and human-in-the-loop review/approval for code changes and other risky actions.
6. RBAC on the model registry and inference endpoints — role-based permissions separating experiment/fine-tune, deploy, and consume; plus scoped API tokens (or OAuth) for the external partners' inference-only access. ABAC could add contextual conditions (device, time, location).
7. A prompt firewall with bidirectional filtering — it inspects and sanitizes inbound prompts (blocking injections and policy violations) and can review outbound responses. The WAF filters HTTP traffic for web exploits like SQL injection and XSS against web applications; it does not understand LLM prompts — both are layered in practice.
8. Network isolation: host the endpoint in a private network or cloud subnet (e.g., a VPC), reachable only through secure gateways, with IP allowlisting/NACLs restricting which systems and users can connect, plus enforced authentication at the API layer and TLS in transit.
9. A shared organization-wide key is a standing, over-privileged bearer credential — whoever holds it reaches every endpoint (embeddings, fine-tuning, admin/management), and rotating or revoking it breaks every consumer at once. Better design: endpoint access controls plus per-application scoped credentials (or OAuth clients) — each consumer authenticates with its own identity, limited by RBAC to its specific endpoint, with rotation and usage quotas per key.
