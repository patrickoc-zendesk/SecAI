# 14. Encryption and Data Safety

> [!info] Exam alignment
> **Domain:** 2.0 — Securing AI Systems (40%)
> **Objectives:** 2.4 — Given a scenario, implement data security controls for AI systems
> **Source notes:** `../14. Encryption and Data Saftey/` (6 files)

## Overview

Objective 2.4 splits into two halves that the exam treats as one scenario space: **encryption requirements** for data in transit, at rest, and in use, and **data safety** techniques — anonymization, classification labels, redaction, masking, and minimization. The "in use" state is the most AI-specific of the three: training and inference both require active computation over data, and confidential computing and homomorphic encryption exist precisely because traditional encryption stops protecting data the moment it is loaded into memory. The data-safety half is classic applied-decision territory — expect scenarios describing how data is collected, prepared, shared, or sent to a model, with four plausible-but-wrong technique options. These controls also shrink the blast radius of the attacks in [[10. Model Extraction and Information Leakage Attacks|Module 10]], protect what a RAG system retrieves in [[05. RAG|Module 05]], and map onto lifecycle stages from [[06. Security in the AI Lifecycle|Module 06]].

## Encryption requirements

Encryption protects data in each of its three states, and an AI system moves data through all three constantly: datasets are transferred between pipeline stages (in transit), stored as training sets, model artifacts, feature stores, and logs (at rest), and loaded into memory for training and inference (in use). An answer that only covers one state is incomplete — reason about where the data is at the moment of the described risk.

### In transit

- Data moving over networks between systems and their components — for example, API calls between services, prompts and responses traveling to and from a model endpoint, dataset transfers between pipeline stages, and retrieval traffic in a RAG system.
- Prevents interception (eavesdropping and on-path attacks) and protects integrity as well as confidentiality.
- **TLS and HTTPS must be used** to protect the confidentiality and integrity of information in motion.
- Service-to-service traffic in AI pipelines can additionally use mutual TLS (mTLS) so both endpoints authenticate each other before any data — including model weights or embeddings — is exchanged.
- The same requirement applies to AI-specific transfers: moving model artifacts or large datasets between environments, syncing data into a vector store, and the update channels that federated learning participants use to reach the aggregator.

### At rest

- Stored data of every kind: **training datasets, model artifacts (weights and checkpoints), feature stores, and system logs**.
- Implemented through storage- and volume-level encryption — full-disk or volume encryption, database encryption, and encrypted object storage. AES-256 is the typical symmetric standard.
- Encryption at rest limits the damage from stolen disks, snapshots, or backups, and from an attacker who gains read access to the storage layer.
- Key management is part of the control: keys held in a managed KMS or HSM with **key rotation**, so encrypted data does not silently become unprotected because a key leaked or never changed. Key rotation is also something auditors verify — see [[15. AI Monitoring and Auditing|Module 15]].
- At-rest encryption applies to AI-derived stores too, not just source datasets: **embeddings and vector stores** built for RAG are derived from source documents and remain sensitive — encrypt them like any other data store.

### In use

Data actively being used for computation is the hardest state to protect: traditionally, data must be **unencrypted in memory** for the processor to work on it — exactly when training and inference happen. Two technologies address this directly, plus one architectural control:

- **Confidential computing — Trusted Execution Environment (TEE).** A hardware-based TEE creates a safe, encrypted memory region (an **enclave**) in which data can be decrypted and processed. Even the host operating system, hypervisor, and cloud provider cannot read what is inside the enclave. **Attestation** lets a relying party verify that the expected code is genuinely running in the enclave before sending it sensitive data. Well-known TEE technologies include Intel SGX, AMD SEV, and AWS Nitro Enclaves.
- **Homomorphic encryption.** Enables computations to be performed **directly on encrypted data**, and the results are also encrypted — only the holder of the decryption key can read the output, and the data is never decrypted anywhere in the pipeline. The trade-off is severe: it is **very resource intensive**, to the point that fully homomorphic encryption (arbitrary computations) is impractical for large-scale model training or inference today. Partially homomorphic schemes support only a single operation type (for example, only addition or only multiplication) and perform better, but are correspondingly limited.
- **Federated learning (data-movement control).** Not encryption itself, but an architectural answer to the same problem: raw data never leaves its source system. Each participant trains locally and only **model updates (gradients) move** to a central aggregator that merges them into a shared model. This keeps raw training data out of transit and central storage — but the updates themselves can leak information about the training data, so federated learning is typically paired with secure aggregation (the server sees only the merged update) and differential privacy, at the cost of communication overhead and orchestration complexity.

In-use protection trade-offs:

| Approach | What it protects | Performance cost | Best fit |
| --- | --- | --- | --- |
| TEE / confidential computing | Data in memory during processing, isolated from the OS, hypervisor, and provider | Moderate overhead; enclave memory is limited | General-purpose training and inference where data must be decrypted but the environment is untrusted |
| Homomorphic encryption | Data throughout computation — never decrypted anywhere | Very high; resource intensive | Narrow, high-sensitivity computations where performance is secondary |
| Federated learning | Raw data at its source — never moved | Communication overhead; orchestration complexity | Distributed data estates where centralizing raw data is unacceptable |

Exam heuristic: "process data at a provider we don't fully trust, performance must stay acceptable" → TEE. "Data must never be decrypted, even in memory, and cost is acceptable" → homomorphic encryption. "The data cannot leave its source systems" → federated learning.

One further point the exam rewards: encryption — even perfect in-use encryption — does not stop the **model itself** from memorizing sensitive training data and regurgitating it later. That residual risk belongs to the data-safety half of the objective (minimize, anonymize, redact before training) and to the leakage attacks in [[10. Model Extraction and Information Leakage Attacks|Module 10]].

## Data safety: the five techniques side by side

This is the mandatory compare-and-contrast table — the five objective techniques plus pseudonymization, the lookalike that makes the classic exam trap:

| Technique | What it does | Reversibility | Classic AI use |
| --- | --- | --- | --- |
| **Anonymization** | Irreversibly removes or generalizes direct and indirect identifiers so records cannot be traced back to an individual | Irreversible | Sharing datasets for analysis or research with no need to re-identify |
| **Pseudonymization** *(contrast — not full anonymization)* | Replaces identifiers with fictitious values; the linking key is stored separately and securely | Reversible with the key | When relationships between records must be maintained for later re-linking |
| **Classification labels** | Tags data with a sensitivity level or type so the right controls follow the data | N/A — metadata, not a transformation | Deciding which protections, sharing rules, and retention apply to datasets, models, and outputs |
| **Redaction** | Removes or destroys sensitive content from the data | Destructive — the content is gone from the output | Scrubbing PII from prompts, outputs, and documents before model use or RAG ingestion |
| **Masking** | Replaces sensitive values with fictitious but plausible placeholders that preserve structure | Static copies are irreversible; dynamic masking is reversible by design because originals remain in the database | Preparing training data; one central database serving multiple environments |
| **Minimization** | Collect, use, and retain only the minimum data needed for the purpose | N/A — limits what exists in the first place | Design-time decisions on prompts, outputs, features, identifiers, and retention |

## Data classification labels

- Assigning labels to data based on levels of **sensitivity, criticality, and compliance requirements**.
- Common label schemes use levels such as:
  - Public
  - Internal
  - Confidential
  - Secret
- Or types such as:
  - PII
  - Financial data
  - Health data
  - GDPR-regulated data
- Classification gives structure to how data is managed: it determines how data is **shared, accessed**, and which protections apply. Labels make the controls "follow the data" — a Confidential dataset automatically inherits Confidential handling — and they feed the access-control decisions covered in [[13. AI Access Controls|Module 13]].
- Classification should apply to **training datasets, models, and outputs** — not just raw data. A model trained on Confidential data inherits that sensitivity (models can memorize), and outputs can contain material drawn from sensitive sources.
- Benefits:
  - Helps apply the correct security controls.
  - Assists in regulatory compliance.
  - Enables the correct management of data across its life.
- AI can itself be used to help assign classification labels (for example, automated PII detection and labeling at ingestion), which is a recurring exam-friendly pattern.
- Labels should **propagate**: a RAG answer assembled from Confidential sources is itself Confidential; a fine-tune built from regulated health data inherits the regulatory constraints. Scenarios often test exactly this inheritance through the training data → model → output chain.

## Data anonymization

- Removing or modifying identifiers in a dataset so that data **cannot be traced back to an individual**.
- Should happen **as early as possible in the data pipeline** — every downstream store, log, and copy then holds only the de-identified form.
- Must remove both:
  - **Direct identifiers** — name, email address, government ID.
  - **Indirect (quasi-)identifiers** — attributes that in combination can re-identify someone, such as date of birth plus postal code plus job title.
- Standard anonymization techniques:
  - **Generalization** — replacing exact values with broader ones (birth year instead of full date of birth).
  - **Suppression** — removing values that cannot be generalized safely.
  - **k-anonymity** — ensuring each record is indistinguishable from at least k−1 other records on the identifying attributes, so no single person stands out.
- Anonymized is not automatically safe forever: **linkage attacks** combine a "de-identified" dataset with other available datasets to re-identify individuals — which is why quasi-identifiers must be generalized or suppressed too, not just the obvious direct identifiers.
- **Pseudonymization contrast (the classic trap):** pseudonymization replaces identifiers with fictitious values, but the **key linking the data back is stored securely**, so it is **usually reversible** — it is therefore not full anonymization. Use it when maintaining relationships between records is essential; use masking when realism matters more than traceability. Under GDPR, pseudonymized data is still personal data, precisely because re-identification with the key remains possible.
- **Synthetic data:** realistic-looking generated data enables analysis and development without risking privacy — no real individual's record is behind any row.

## Data redaction

- The process of **removing or obscuring sensitive information** — destruction of the sensitive content rather than replacement (compare masking, which substitutes a plausible placeholder and preserves structure).
- In AI systems, redaction protects privacy on both sides of the model:
  - **Input side:** prompts can be preprocessed to redact sensitive data, so only the obfuscated version is used in the final prompt sent to the model.
  - **Output side:** post-processing can remove sensitive data from model outputs before they reach the user or downstream systems.
- Redaction ensures private details are obscured **during retrieval in RAG systems** — scrub documents at ingestion so nothing sensitive is ever indexed and retrievable (see [[05. RAG|Module 05]]).
- **Context is critical** to successful redaction — a bare pattern match misses PII that only context reveals (a name that looks like a common noun, an ID embedded in prose). Rule-based tools and AI models can be combined to achieve context-aware redaction.
- Redacting data in **images, video, or audio files** usually requires specialized tools (blurring regions, muting segments) — text-oriented redaction pipelines do not transfer.

## Data masking

- A technique used to protect sensitive information by **replacing it with a fictitious value**.
- **Preserves the structure and usefulness of the data** without exposing private details — masked data still behaves like real data for development, testing, and training. **Format-preserving masking** goes further and keeps the original format (a masked card number still looks like a card number), so downstream systems and model features continue to work.
- In AI systems, masking is a **common technique when preparing training data**.
- Two ways to apply it:
  - **Static** — permanently masks a copy of a dataset. The masked copy is irreversible, which suits training data and non-production environments.
  - **Dynamic** — replaces values in real time as data is accessed, **based on permissions**. Useful when multiple systems share a central database: production uses unmasked data while staging gets masked versions of the same record. Because the original values remain in the database, dynamic masking is reversible by design for authorized users.
- Masking should be **combined with other approaches** to enhance effectiveness — for example, use generalization as well (only show birth year when the input is a date of birth).

## Data minimization

- The principle of **collecting, using, and keeping the minimum amount of data needed** for a specific purpose.
- Highly effective at reducing security risk and is a **core GDPR principle** — compliance and security pull in the same direction here.
- In AI systems, minimization applies across the whole pipeline:
  - **Decide what is truly necessary to train the model** — remove unnecessary identifiers to reduce risk.
  - **Limit prompt content** — only necessary information should go into the prompt.
  - **Minimize prompt outputs** — responses should contain only necessary information; this strengthens both user experience and privacy.
  - **Shorten data retention** — retain conversation logs only as long as needed, then delete them.
  - **Minimize feature size** — use only the features required for the model to perform its task.
- Why it matters for security: data that was never collected or already deleted cannot be breached, subpoenaed, or extracted. Minimization directly reduces what an attacker can obtain through [[10. Model Extraction and Information Leakage Attacks|Module 10]] (extraction and membership leakage) and limits what a RAG pipeline can ever retrieve about individuals ([[05. RAG|Module 05]]).

## Choosing the right technique for the scenario

The exam shape is "given this situation, which control applies?" Map each scenario to its technique:

| Scenario | Correct technique | Why |
| --- | --- | --- |
| Preparing production records as a training set for a non-production environment | Static masking | A permanently masked copy protects privacy while the copy remains useful |
| One central database serves production and staging; each environment should see different values for the same record | Dynamic masking | Real-time, permission-based replacement; originals stay in the database |
| Sharing a dataset externally for research where nobody ever needs to re-identify individuals | Anonymization (generalization, suppression, k-anonymity) | Irreversible — no key, no re-identification path |
| Identifiers must be protected now but records must be re-linkable later | Pseudonymization | Reversible via the securely stored key; preserves record relationships |
| Free-text prompts or documents contain PII before third-party model use or RAG ingestion | Redaction | Context-aware removal of the sensitive content itself |
| Deciding whether data should be collected or kept at all | Minimization | Reduces what exists — breach and leakage exposure shrink at the source |
| A new dataset arrives and you must determine which protections apply | Classification labels | Labels are decided first; they drive which of the other controls apply |

A useful decision path for scenarios: **label first** (classification) → **minimize** (is this data needed at all?) → **de-identify what remains** (anonymize / pseudonymize / mask / redact, chosen by re-linking and structure needs) → **encrypt what stays** in all three states.

### Combining the controls

The two halves of the objective are complementary, and scenarios often need several controls stacked rather than one "best" control:

- **Encryption protects the container; data safety shapes the content.** Encryption at rest protects the dataset from a storage-layer thief, but it does nothing about what the model memorizes, what a prompt reveals, or what a response leaks — that is the data-safety half's job.
- **Controls compose at different pipeline points.** A realistic secure RAG assistant stacks them: classify source documents at ingestion → minimize what is collected → redact PII before documents are indexed → mask any training copies → encrypt the vector store and logs at rest → use TLS for every retrieval and inference call → bound log retention.
- **Redaction and masking can work together** — redact content that should not exist anywhere downstream, mask values that must remain structurally present.
- **Anonymization is strongest earliest.** De-identify as close to the source as possible so no downstream store, log, or backup ever holds identified data.
- Watch for scenario answers that present a single control as sufficient when the described system needs the layered stack — the strongest option is usually the one that acknowledges both halves of the objective.

## Where these controls fit in the AI lifecycle

Objective 2.4 is scenario-based, and lifecycle placement is a favorite scenario axis (see [[06. Security in the AI Lifecycle|Module 06]]):

- **Collection / ingestion** — classification labels and minimization decisions (what to collect at all).
- **Preprocessing / training data preparation** — anonymization as early as possible in the pipeline; static masking of training copies.
- **Training and inference (data in use)** — TEE-based confidential computing or homomorphic encryption; federated learning where raw data cannot be centralized.
- **Deployment / serving** — redaction of prompts before they reach the model and of outputs after; dynamic masking over shared databases; minimized prompt and output content.
- **Throughout** — encryption in transit for every transfer (pipeline stages, API calls, retrieval traffic), encryption at rest for datasets, model artifacts, feature stores, and logs, and bounded log retention.

## Exam Focus

- **Exact objective wording:** "Given a scenario, implement data security controls for AI systems." Sub-items: encryption requirements (in transit; at rest; in use) and data safety (data anonymization; data classification labels; data redaction; data masking; data minimization).
- **Compare-and-contrast pairs to master:**
  - Anonymization vs pseudonymization — irreversible vs reversible via a securely stored key.
  - Masking vs redaction — replace with a plausible placeholder preserving structure vs remove/destroy the content.
  - Static vs dynamic masking — permanent masked copy vs real-time permission-based replacement (originals persist).
  - Masking vs anonymization — realism and structure preservation vs untraceability to any individual.
  - Minimization vs the other four — limits what data exists vs transforms data that exists.
  - TEE vs homomorphic encryption vs federated learning — isolated decrypted processing vs compute on ciphertext vs data never moves.
  - In transit vs at rest vs in use — TLS vs storage/volume encryption vs confidential computing.
- **Classic distractor confusions:**
  - Pseudonymization offered as "anonymization" — wrong because it is reversible, and pseudonymized data is still personal data under GDPR.
  - Masking offered as anonymization, and vice versa.
  - Redaction and masking swapped (destruction vs substitution).
  - "We anonymize everything" offered when the scenario actually needs minimization (not collecting/keeping it at all).
  - TLS offered as an at-rest control, or disk encryption offered for data in use.
  - Federated learning presented as an encryption method — it is a data-movement/architectural control.
  - Dynamic masking presented as irreversible — it is reversible by design.
- **Likely scenario shapes:**
  - Choose the data-safety technique for preparing training data, sharing a dataset, scrubbing prompts, or ingesting documents into RAG.
  - Choose the in-use encryption approach given performance, trust, and data-locality constraints.
  - Pick the control that best satisfies a GDPR-style privacy requirement (minimization, early anonymization, retention limits).
  - Identify which state (transit/rest/use) a described risk applies to, and the matching encryption requirement.

## Key Terms

| Term | Definition |
| --- | --- |
| Encryption in transit | Protecting data moving over networks between systems and components via TLS/HTTPS |
| Encryption at rest | Protecting stored data — training datasets, model artifacts, feature stores, logs — via storage/volume encryption |
| Encryption in use | Protecting data while it is actively being computed on |
| Confidential computing | Computing in a hardware-isolated environment so data is protected even while in use |
| Trusted Execution Environment (TEE) | Hardware-based secure memory region (enclave) for safe processing, invisible to the OS, hypervisor, and provider |
| Enclave | The encrypted memory region created by a TEE |
| Attestation | Verification that expected code is genuinely running inside a TEE before data is sent to it |
| Homomorphic encryption | Encryption that allows computation directly on encrypted data, producing encrypted results |
| Federated learning | Architecture in which raw data stays at its source and only model updates move to a central aggregator |
| Secure aggregation | Combining participant updates so the server sees only the merged result |
| Data anonymization | Irreversibly removing or generalizing identifiers so data cannot be traced back to an individual |
| k-anonymity | Each record is indistinguishable from at least k−1 others on the identifying attributes |
| Generalization | Replacing exact values with broader ones (birth year instead of date of birth) |
| Suppression | Removing values that cannot be safely generalized |
| Quasi-identifier | An attribute that in combination with others can re-identify an individual |
| Pseudonymization | Replacing identifiers with fictitious values while a securely stored key preserves re-linkability |
| Synthetic data | Realistic generated data that enables analysis without real privacy risk |
| Data classification labels | Sensitivity/criticality/compliance tags that determine how data is shared, accessed, and protected |
| Data redaction | Removing or obscuring sensitive information from data, prompts, outputs, or documents |
| Data masking | Replacing sensitive values with fictitious values that preserve structure and usefulness |
| Static masking | Permanently masking a copy of a dataset |
| Dynamic masking | Replacing values in real time based on permissions, with originals kept in the database |
| Format-preserving masking | Masked values keep the original format so downstream systems still work |
| Data minimization | Collecting, using, and keeping only the minimum data needed for a specific purpose |
| Data retention | How long data (including conversation logs) is kept before deletion |
| mTLS (mutual TLS) | TLS variant in which both endpoints authenticate each other before exchanging data |
| Linkage attack | Re-identifying "anonymized" records by combining them with other datasets |
| Differential privacy | Adding calibrated noise so individual records cannot be inferred from aggregate outputs or updates |

## Self-Check

1. A research team wants a copy of customer records to train a model in a staging environment. The records must remain realistic and structurally valid, and the staging copy should never expose real customers. Which control fits best?
2. An organization must share an aggregated dataset with an external partner, and no individual must ever be re-identifiable from it. A proposal is put forward to replace names with random IDs and store the mapping in a key vault. What is the flaw?
3. A single central database serves production and staging. Production applications must see real values; staging must never see them. Which technique applies?
4. Before free-text support tickets are sent to a third-party model API, customer names, card numbers, and addresses must be removed — the sensitive content itself should not survive into the prompt. Which technique applies, and what is the main implementation challenge?
5. A privacy regulator asks why an AI system stores full dates of birth in training data when birth year is sufficient for the model's task. Which two principles or techniques are in play?
6. A company wants to run model inference on sensitive data hosted at a cloud provider it does not fully trust. Performance must remain acceptable and general-purpose computation is needed. Which approach fits, and what lets the company verify it?
7. Which of the three encryption states does a traditional encryption strategy leave exposed during model training, and what are the two technologies that address it?
8. A new dataset arrives with no marking of its sensitivity. What is the first data-safety control to apply, and what does it determine?

### Answers

1. **Static masking.** A permanently masked copy protects privacy while preserving realistic structure for training — exactly the static-masking use case. (Dynamic masking would leave the originals in the production database; anonymization would be needed only if the goal were untraceability rather than realism.)
2. Random IDs with a stored mapping is **pseudonymization, not anonymization** — it is reversible with the key, so the data remains re-identifiable (and remains personal data under GDPR). The scenario requires irreversible anonymization: generalization, suppression, and k-anonymity.
3. **Dynamic masking.** Values are replaced in real time based on permissions; production sees unmasked data, staging sees masked versions of the same records, and originals stay in the central database.
4. **Redaction** (as prompt preprocessing). The content is removed rather than replaced. The challenge is context — bare pattern matching misses sensitive data only context reveals, so rule-based tooling and AI models are combined; redaction in images, video, or audio needs specialized tools.
5. **Data minimization** (birth year is sufficient, so full DOB is more than the purpose needs) and **generalization** (birth year is the generalized form of DOB). Minimization is the GDPR principle; generalization is the anonymization/masking technique that implements it.
6. **Confidential computing in a Trusted Execution Environment (TEE)** — encrypted enclaves (for example SGX-style) allow decryption only inside hardware-isolated memory the provider cannot read, with acceptable overhead for general-purpose computation. **Attestation** lets the company verify the expected code is running in the enclave before sending data.
7. **In use.** Traditionally data must be unencrypted in memory for computation, including during training. The two technologies are **confidential computing (TEE)** and **homomorphic encryption**; federated learning is the related architectural control that keeps raw data at its source.
8. **Data classification labels.** They determine how the dataset is shared, accessed, and protected — and which of the other data-safety and encryption controls apply to it (and to any model trained on it).
