# 04. Data Processing

> [!info] Exam alignment
> **Domain:** 1.0 — Basic AI Concepts Related to Cybersecurity (17%)
> **Objectives:** 1.2
> **Source notes:** `../04. Data Processing/` (8 files)

## Overview

This module covers the data processing techniques that keep AI training data accurate, authentic, and traceable, together with the three data types AI systems consume and watermarking for content and model protection. Objective 1.2 — "Explain the importance of data security in relation to AI" — treats data quality as a security property: a model trained on cleansed, verified, provenance-tracked data resists poisoning and supports audits, while dirty or unverified data is the raw material for poisoning, bias, and unreliable model behavior. Expect scenario-based questions that describe a pipeline problem (mislabeled records, an imbalanced fraud corpus, a suspicious third-party feed) and ask which technique applies and at which pipeline stage it belongs. Two of the most heavily tested compare-and-contrast pairs live in this module: **data lineage vs. data provenance** and **data augmentation vs. data balancing**.

The module's mental model: staged quality gates — cleanse the data, verify it, track it (lineage and provenance), then balance or augment it — where each gate blocks a different failure mode: dirty data, tampered data, untraceable data, or biased data.

## Data Types: Structured, Semi-Structured, and Unstructured

AI systems depend on three categories of data. The category determines the attack surface and the controls that fit — a recurring "match the control to the data type" scenario shape.

| Type | Format | Examples | Security considerations | Key protections |
| --- | --- | --- | --- | --- |
| Structured | Fixed, predefined format with clearly defined fields | Relational databases, tables, spreadsheets | High-value target: one compromise exposes many queryable records at once | Strong access control management, encryption in transit and at rest, regular audits, integrity checks to identify unauthorized changes |
| Semi-structured | Partial organization via tags or key-value pairs; no rigid schema | JSON, XML, email headers | Both data and metadata need protection; schema flexibility lets harmful data slip in unnoticed | Encrypt data and metadata, monitor API activity, validate inputs and outputs to block harmful data before it enters the system |
| Unstructured | No predefined structure or organization | Text documents, social media posts, audio files, images, videos | Hard to categorize and therefore tricky to secure; easily contains sensitive information and hidden identifiers | File-level encryption, redaction tools, metadata sanitization to remove hidden identifiers or location tags |

### Structured data

- Neatly organized in a fixed, predefined format with clearly defined fields — the easiest type to search, join, and exfiltrate in bulk.
- Security-relevant examples: customer PII in a relational database, transaction tables used to train a fraud model, asset inventories feeding a risk-scoring system.
- Because it concentrates high-value data, it is a primary target for attackers; controls center on access control, encryption, auditing, and integrity checking of every change.

### Semi-structured data

- Combines characteristics of both other types: partially organized through tags or key-value pairs, but without a rigid schema.
- Security-relevant examples: SIEM and application log events shipped as JSON, XML configuration and API payloads, email headers (which carry spoofable identity fields).
- Security significance: schema-on-read flexibility means validation is the key control — malformed or hostile content (injection payloads hidden in log fields, for example) must be caught at input/output boundaries, and metadata (tags, headers) must be encrypted and monitored just like the payload.

### Unstructured data

- Lacks predefined structure or organization: more flexible, but more difficult to manage, categorize, and secure.
- Security-relevant examples: incident response reports, support tickets containing PII, social media feeds, images with EXIF GPS metadata, steganography hidden inside image or audio files, video from security cameras.
- Sensitive information hides easily — redaction, file-level encryption, and metadata sanitization (stripping location tags and hidden identifiers) are the signature controls for this type.

**Exam tip — match the control to the type.** A scenario about hidden GPS tags in photos points to metadata sanitization on unstructured data; malformed JSON records entering training point to input/output validation on semi-structured data; bulk exfiltration of customer records points to access control and encryption on structured data. When a question names a data format, the format tells you the intended control.

## Data Cleansing

**Definition.** Data cleansing is the process of identifying errors, inconsistencies, and irrelevant data **before it reaches the training pipeline** so that the data is accurate and consistent.

- Typical operations: fixing typographical errors, filling in missing values, standardizing formats, eliminating duplicate or incomplete records.
- Cybersecurity-flavored examples: removing log entries with invalid timestamps, correcting inconsistent log formats, flagging sensor readings that fall outside realistic ranges.
- **Why it matters for model trustworthiness:** it prevents models from learning incorrect patterns — a model trained on duplicated or mislabeled records will reproduce those flaws at inference time.
- Indirect security benefit: a cleansing pass can identify attack payloads (e.g., SQL injection strings embedded in scraped logs) before that data is used to train the model, so the model never bakes hostile content into its behavior.
- **Attack linkage:** poor cleansing enables data poisoning — malicious or malformed records that survive into training skew the trained model. See [[08. Data and Training Attacks|Module 08]].
- Concrete example: a phishing-classifier trained on an email corpus containing duplicated legacy campaign mail and mislabeled samples will overfit the duplicates and systematically miscategorize; deduplication and label correction are the fix.
- Pipeline position: cleansing is the earliest quality gate — it runs before verification, and neither substitutes for the other. Cleansing fixes what the data says; verification checks who it came from and whether it was altered in transit.
- A cleansing log is also accountability evidence: a record of what was fixed, deduplicated, or removed, and when.
- Pipeline order on the exam: cleanse → verify → balance/augment → train. The notes make the first two explicit ("once data is cleaned it needs to be verified"); a scenario listing format fixes first and authenticity checks second is testing that you know both gates and their order.

## Data Verification

**Definition.** Once data is cleaned, it must be verified as genuine, intact, and traceable to a trusted source. Verification involves comparing data against trusted references or known standards — cross-referencing internal records, internal databases, or authoritative sources.

- Cryptographic tools support verification: checksums and hashes (e.g., `SHA-256`) detect modification during transfer or while in storage.
- Verification ensures models are only trained on trusted data that has not been tampered with.
- **Verification vs. validation (a classic distractor):** verification confirms data is authentic and unaltered; validation confirms it meets format and business rules. A field can be perfectly valid (right type, right format) and still be forged.
- Concrete example: a threat intelligence vendor publishes a daily indicator feed with a signed hash; the pipeline recomputes the hash at ingestion and quarantines the feed on mismatch — tampering in transit never reaches training.
- **Attack linkage:** skipping verification is how poisoned third-party data enters a training set (Module 08).
- Trusted-reference examples: cross-referencing new records against internal databases, comparing against authoritative sources, and checking signatures on signed feeds.
- Operational best practice: quarantine mismatches rather than silently dropping them, so analysts can investigate suspected tampering and the pipeline keeps an auditable trail.

| Aspect | Data cleansing | Data verification |
| --- | --- | --- |
| Goal | Fix errors and inconsistencies (hygiene) | Confirm data is genuine, intact, and from a trusted source |
| Question answered | "Is the data accurate and consistent?" | "Is the data authentic and untampered?" |
| Pipeline position | First, before verification | After cleansing, before training |
| Techniques | Deduplication, format standardization, missing-value handling, outlier flagging | Cross-referencing trusted sources, checksum/hash comparison (`SHA-256`), source attestation |
| If skipped | Model learns incorrect patterns | Tampered or poisoned data trains the model undetected |

## Data Integrity

**Definition.** Data integrity is the protection of information from unauthorized alteration, keeping data consistent, accurate, and reliable across its entire lifecycle. It is one of the three pillars of the CIA triad (confidentiality, integrity, availability).

- AI-specific significance: small changes can have large effects on model behavior — models are not linearly "proportional" to their inputs, so a subtle training-data edit can produce a subtly wrong model.
- Controls that safeguard integrity: digital signatures, cryptographic hashes, and version control systems that track every modification.
- Access control limits `CRUD` (create, read, update, delete) operations on the data.
- Integrity also includes accountability: being able to show who changed what, and when.
- Concrete example: a training dataset lives in a versioned repository with signed commits; any after-the-fact edit to the corpus is visible in the diff history, and the model build record pins the exact dataset version used.
- In AI pipelines, integrity spans more than the dataset: model artifacts (checkpoints, weights) and evaluation sets also need tamper protection — a swapped checkpoint poisons the model without ever touching the training data.
- Accountability thread: signed, version-controlled datasets let you prove exactly which data trained which model — the evidence an auditor or incident responder will ask for.

| Aspect | Data integrity | Data verification |
| --- | --- | --- |
| Nature | A property/state to be maintained (ongoing, lifecycle-long) | An action/control performed (a point-in-time check) |
| Goal | Data remains consistent, accurate, and reliable for its entire lifecycle | Confirm data is genuine, intact, and traceable to a trusted source |
| Typical controls | Digital signatures, hashes, version control, CRUD access control | Cross-referencing trusted references, checksum comparison |
| Relationship | The thing you protect | The way you check the protection held |

## Data Lineage and Provenance

These two concepts travel together and are a **classic distractor pair** — the exam will offer both as options and expect you to pick the right one.

- **Data lineage** documents the full path the data takes from source to final use, including every transformation, aggregation, and processing step.
  - This visibility enables error tracing, result explanation, and reproduction of past experiments (essential for model audits and debugging bad outputs).
- **Data provenance** documents the origin and authenticity of the data itself. It answers: Who created the data? Where was it first collected? Does it come from a reliable source?
  - Very important for regulated industries (compliance reporting, auditability) — see [[20. AI GRC|Module 20]].
- Together they strengthen transparency and accountability and help detect supply-chain risks such as poisoned or unlicensed data entering the training set.
- Concrete example: an audit finds a biased model outcome. **Lineage** traces the output back through the joins and transformations to the exact intermediate tables that produced the training set; **provenance** then reveals that one contributing source was an unvetted scraped dataset — the two answers together close the case.
- **Exam tip:** when the scenario describes a *journey* (joins, transformations, aggregations, pipelines), pick lineage; when it describes a source's *credibility or licensing* (who collected it, is the source reliable, is it licensed for training use), pick provenance.

| Aspect | Data lineage | Data provenance |
| --- | --- | --- |
| Focus | The journey — the lifecycle record of where data came from and how it transformed | The origin — the birth record of the data itself |
| Records | Every transformation, aggregation, and processing step from source to final use | Creator, first collection point, source reliability, ownership/attestation |
| Answers | "What happened to this data on its way here?" | "Where did this data come from, and can the source be trusted?" |
| Security use | Trace a bad model output to the exact pipeline step that introduced it | Reject data from untrusted or unlicensed sources at ingestion |
| Mnemonic | The path | The birth certificate |

## Data Augmentation

**Definition.** Data augmentation enhances the size and variety of training data by creating new examples from existing ones, addressing the common AI problem of not having enough diverse or balanced data.

- Classic example: for images, applying rotation, flipping, cropping, scaling, or noise to existing samples.
- Benefits: enhanced model performance, improved resilience to adversarial actions, reduced data-acquisition cost, and reduced overfitting by exposing the model to greater variation.
- **Why it matters for trustworthiness:** a model that has seen many legitimate variations of the same input is harder to fool with small perturbations — augmentation is a defensive technique against evasion-style attacks (Module 08).
- **Security caveat (exam-relevant):** augmentation amplifies whatever it is given. Augmenting a poisoned or mislabeled sample multiplies the poison; augmented data still needs cleansing and verification first.
- Concrete example: a malware-detection model trained on a few thousand samples per family; adding resized, noised, and re-packed variants of known malware improves detection of small mutations of those families.

## Data Balancing

**Definition.** Data balancing addresses class imbalance — where some classes of data are far more common than others — by adjusting how the training data is distributed, so the model can make fair and accurate decisions.

- Techniques:
  - **Oversampling:** increase the number of minority-class examples by duplicating or synthetically creating new records.
  - **Undersampling:** reduce the number of majority-class samples so the dataset is more even.
  - **SMOTE (Synthetic Minority Oversampling Technique):** creates realistic new samples of the underrepresented class without duplication, by interpolating between existing minority-class examples.
- **Security relevance:** imbalanced data causes models to miss rare events such as intrusions or fraud — a high false-negative rate. A model trained on 99% benign network traffic can label almost everything benign and still look highly accurate; balancing is what makes the rare class learnable.
- Fairness relevance: class imbalance across demographic groups produces biased outcomes.
- Concrete example: a fraud model trained on a real transaction corpus where 0.5% of records are fraud; without balancing (e.g., SMOTE on the fraud class), the model optimizes for the majority class and lets fraud through.

| Aspect | Data augmentation | Data balancing |
| --- | --- | --- |
| Goal | Expand training data size and variety | Correct class imbalance in the existing training data |
| Problem addressed | Not enough diverse data; overfitting | Some classes far more common than others; bias and missed rare events |
| Method | Create new examples from existing ones (rotation, flipping, cropping, scaling, noise) | Oversampling, undersampling, SMOTE |
| Trigger scenario | "We only have 500 labeled images" | "Only 0.5% of our records are attacks" |
| Security angle | Adversarial robustness; reduced overfitting | Catching rare intrusions/fraud (avoiding high false negatives); fairness |
| Distractor trap | SMOTE is a *balancing* technique, not augmentation | Augmentation does not fix a skewed class distribution |

## Watermarking

**Definition.** Watermarking embeds a hidden signature or pattern in data or a model. It helps verify ownership, detect tampering, and prove authenticity long after the content has left its original source. Watermarking serves three main purposes: supporting provenance (identifying what model created the content), supporting intellectual property protection, and helping preserve integrity.

- In practice, watermark detection doubles as a tamper check: a watermark that no longer decodes correctly signals the content was modified after it left its source.

The exam uses **two distinct angles** — do not conflate them:

### Watermarking AI-generated content (provenance / disinformation defense)

- Used to label AI-generated content, helping counter deepfakes and misinformation: a durable watermark lets a downstream verifier determine that an image, audio clip, or text was machine-generated and by which model family.
- This is a provenance control — it answers "is this content authentic, and where did it come from?" in the fight against disinformation.
- Industry examples include Google DeepMind's SynthID and the C2PA Content Credentials standard.
- Exam-relevant caveat: watermarks vary in robustness — some can be stripped or degraded by re-encoding, cropping, or regeneration, so watermarking is a mitigation, not a guarantee.

### Watermarking models and data to detect theft (IP protection)

- A model can be watermarked during training so it responds distinctively to a secret set of trigger inputs. If a competitor's product (possibly produced via model extraction) emits the distinctive responses when probed with those triggers, that is evidence the model was copied or distilled.
- This links directly to model extraction attacks — see [[10. Model Extraction and Information Leakage Attacks|Module 10]].
- Datasets can likewise be watermarked so unauthorized use in someone else's training pipeline can be proven (provenance plus IP protection).
- Concrete example: a vendor suspects a rival's "independent" model is a knock-off; querying both models with the vendor's private trigger set yields matching distinctive outputs — the watermark has done its job as forensic evidence.

## Exam Focus

- **Exact objective wording (1.2):** "Explain the importance of data security in relation to AI." Data processing sub-items: **data cleansing; data verification; data lineage; data integrity; data provenance; data augmentation; data balancing.** Also in 1.2: data types (structured, semi-structured, unstructured), watermarking, and RAG (see [[05. RAG|Module 05]]).
- **Compare and contrast pairs to master:**
  - Data lineage vs. data provenance — lineage = the path and transformations; provenance = origin, ownership, attestation of the data itself.
  - Data cleansing vs. data verification — fixing errors vs. confirming authenticity against trusted references.
  - Data integrity vs. verification — the ongoing protected state vs. the act of checking.
  - Data augmentation vs. data balancing — expanding size/variety vs. correcting class imbalance.
  - Verification vs. validation — authentic and unaltered vs. conforms to format/business rules.
- **Classic distractor confusions:**
  - Choosing "provenance" when the question describes the data's transformation path (that is lineage).
  - Choosing "augmentation" for an imbalanced dataset (that is balancing — SMOTE included).
  - Treating validation as verification (valid-but-forged data passes validation, fails verification).
  - Forgetting that watermarking covers *both* AI-content labeling and model/data theft detection.
  - Metadata sanitization belongs to *unstructured* data (photos, documents), not structured tables.
  - Confusing data cleansing with data minimization — cleansing improves training data quality; minimization is a privacy control that limits what is collected at all ([[14. Encryption and Data Safety|Module 14]]).
- **Likely scenario shapes:**
  - "At which stage does X control belong": cleanse → verify → train; hash checks at ingestion; version control over the training corpus.
  - A model trained on third-party data misbehaves — which missing control would have caught it (verification/provenance)?
  - A detector keeps missing rare attacks — which data technique fixes it (balancing/SMOTE)?
  - Suspected model theft — which technique provides evidence (model watermarking)?
  - Match the protection to the data type (relational DB vs. JSON logs vs. image corpus).
  - Hidden GPS/location tags in photos → metadata sanitization (unstructured); unlicensed third-party data discovered in a training set → provenance/supply-chain detection; a swapped model checkpoint → integrity of model artifacts.
- Data-safety technique selection (encryption, redaction, anonymization, metadata sanitization) is the natural follow-on — see [[14. Encryption and Data Safety|Module 14]].

## Self-Check

1. A security team ingests a third-party threat intelligence feed into model training. During an audit, they must prove where every record originally came from and that the feed's source is trustworthy. Which two concepts apply, and what does each establish?
2. Before a training run, a team fills missing values, deduplicates records, and standardizes inconsistent log formats. What technique is this, and what training-time risk does it reduce?
3. A dataset transferred between environments fails a `SHA-256` comparison. Which control caught the problem, and which security property was it protecting?
4. A fraud-detection model trained on a production corpus (0.5% fraudulent transactions) labels nearly everything as legitimate while scoring 99% accuracy. Which data processing technique should the team apply, and which specific method creates realistic synthetic minority-class samples?
5. A team multiplies its image corpus by rotating, flipping, and cropping existing samples to reduce overfitting. Which technique is this, and how does it differ from the technique in question 4?
6. A vendor suspects a competitor's model is an unauthorized copy. Which technique gives the vendor forensic evidence, and how does it work?
7. Security camera images are being used for training. Which data-type-specific protection strips GPS coordinates and hidden identifiers from these files?
8. A record passes every format and business-rule check but was actually forged by an insider. Which concept was checked, and which one was skipped?

### Answers

1. **Data provenance** establishes origin, ownership, and source trustworthiness; **data lineage** documents the path and transformations from source to final use. Together they support auditability and detect poisoned or unlicensed data entering the training set.
2. **Data cleansing.** It reduces the risk that the model learns incorrect patterns from dirty data, and limits the opening for data poisoning by malicious or malformed records.
3. **Data verification** (checksum/hash comparison) caught it, protecting **data integrity** — detection of modification during transfer or storage.
4. **Data balancing**, using **SMOTE**. The class imbalance causes high false negatives on rare fraud; balancing makes the rare class learnable. (Oversampling/undersampling are also acceptable balancing answers.)
5. **Data augmentation** — expanding the size and variety of training data to improve robustness and reduce overfitting. It differs from balancing because it does not correct a skewed class distribution; balancing does.
6. **Model watermarking.** A secret trigger set embedded during training makes the model respond distinctively to those inputs; probing the suspect model with the triggers yields matching responses as evidence of copying — the counterpart to model extraction attacks (Module 10).
7. **Metadata sanitization** — an unstructured-data control that removes hidden identifiers and location (EXIF) tags before the files are used or shared.
8. **Validation** was checked (format/business rules were met); **verification** was skipped — the record's authenticity and trusted source were never confirmed.
