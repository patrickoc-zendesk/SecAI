## Overview

Objective 1.1 covers model **training techniques**: model validation, supervised learning, unsupervised learning, reinforcement learning, and fine-tuning — including **epoch**, **pruning**, and **quantization**, which the objective lists explicitly under fine-tuning. The exam tests these as applied decisions: given a data situation (labeled, unlabeled, or interactive) or a model problem (overfitting, drift, size), pick the right technique and know its risks. The training-signal distinction — labels, no labels, rewards — is the single most exam-load-bearing idea in this module, reinforced by federated learning (privacy scenarios) and the overfitting/concept-drift pair that shows up constantly in Domain 2.0 lifecycle questions ([[06. Security in the AI Lifecycle|Module 06]]).

## How Training Works: Loss, Gradient Descent, and Inference

*Grounding from the foundational course notes — one short read, and the rest of this module makes sense.*

- A model is a function with adjustable **parameters** (weights). During **training**, parameters are fit to data; during **inference**, the trained model predicts outputs on new data. Training vs. inference is a security-relevant split: attacks differ by phase (poisoning hits training; injection and extraction hit inference — see [[08. Data and Training Attacks|Module 08]] and [[10. Model Extraction and Information Leakage Attacks|Module 10]]).
- **Loss** measures how poorly the model fits the training data; common loss functions include **mean squared error** (regression) and **cross-entropy** (classification). Lower loss = better fit.
- **Gradient descent** iteratively adjusts parameters in the direction that reduces loss. **Stochastic gradient descent (SGD)** estimates the gradient on a random subset of data per iteration — the **batch** — which is far more efficient on large datasets.
- One full pass over the entire training dataset is an **epoch** (expanded under Fine-Tuning below, where the objective lists it).
- Modern LLMs are **foundation models**: pre-trained on massive unlabeled corpora, then **fine-tuned** for downstream tasks — so fine-tuning needs far less data than training from scratch.

## Supervised Learning

- Trained on a **labeled dataset**: every example in the training data contains the correct answer, and predictions are based on those labeled correct answers.
- Two task families (a favorite exam pair):
  - **Classification** — predicts a categorical value.
    - Example: determining whether an email is spam or not spam; labeling a file malicious or benign; assigning a malware family.
  - **Regression** — predicts a continuous value.
    - Example: forecasting how many attacks a network will face over a period of time.
- A typical supervised security workflow: collect examples (emails, processes, network flows) → analysts label them (malicious/benign, family, severity) → train → validate on held-out data → deploy → monitor for drift.
- Strengths: accurate when good labels exist; outputs are easy to evaluate against ground truth.
- Security-data caveat: attack examples are usually **rare** relative to normal activity, so security datasets are **imbalanced** — raw accuracy is a misleading metric (a model that labels everything "benign" can still score highly). Evaluate with metrics that reflect catching the rare class.
- Limitations (know all three):
  - **High time cost** to label the training data.
  - **Poor-quality labels produce unreliable results** — garbage in, garbage out. An attacker who can influence labels (label poisoning) corrupts the model from the start ([[08. Data and Training Attacks|Module 08]]).
  - **Struggles with new or unseen data**, producing incorrect classification — a labeled model only knows the classes it was taught.

## Unsupervised Learning

- Models explore **unlabeled datasets** with no predefined answers, identifying **patterns and outliers** on their own.
- Techniques:
  - **Clustering** — groups similar data together; used to surface unexpected patterns such as suspicious network traffic (anomalous traffic falls outside the normal clusters).
  - **Dimensionality reduction** — simplifies complex data by removing redundancies and low-value features, making patterns easier to interpret.
    - **Principal Component Analysis (PCA)** is the standard linear dimensionality-reduction technique, frequently used in cybersecurity to reveal patterns and anomalies within large volumes of data such as network traffic.
- Security uses: anomaly detection without needing labeled attack data — anything that deviates from the learned baseline is flagged (insider threat, beaconing, unusual data staging).
- Concrete unsupervised security examples:
  - Grouping similar malware samples into families without labels.
  - User and entity behavior analytics (UEBA): learn each user's normal baseline and flag deviations.
  - Clustering SIEM alerts to surface novel campaigns nobody has labeled yet.
- Limitation: results can be **difficult to interpret** due to the lack of human-type reasoning — an analyst sees a cluster, not a story. Expect high false positives on rare-but-legitimate behavior.

## Reinforcement Learning

- Teaches an **agent** to make adaptive decisions by **interacting with an environment**: the agent takes an action, receives feedback (**a reward or a penalty**), and adjusts its behavior to maximize positive feedback.
- Learns over time and continually improves based on previous results.
- Requires **many iterations** to learn effectively; training often happens in **simulated environments** (cheap, safe failure).
- Security-relevant uses: automating complex decision-making processes, adaptive tuning of response actions, and (with RLHF) aligning LLM behavior.
- Vocabulary: the **agent** acts; the **environment** responds; the **action** changes the environment's state; the **reward/penalty** is the feedback signal the agent learns to maximize.
- **RLHF — reinforcement learning with human feedback** uses **human ratings to shape the reward signal**, and is the standard method for aligning LLM behavior with intended, safe responses.
- RLHF aligns *behavior and preference* — it does not add factual knowledge. Hallucination control needs other measures, such as grounding responses in retrieved sources ([[05. RAG|Module 05]]).
- Security angles:
  - **Reward hacking**: an agent maximizes its reward in unintended, harmful ways — a core risk when giving agents authority (see [[11. Integration and Operational Attacks|Module 11]] on agentic systems).
  - RLHF/human feedback pipelines are a poisoning target: whoever shapes the reward signal shapes the model's values ([[08. Data and Training Attacks|Module 08]]).

## Compare and Contrast: The Three Core Paradigms

| Aspect | Supervised | Unsupervised | Reinforcement |
| --- | --- | --- | --- |
| Training signal | Labeled examples (correct answers given) | No labels — structure found in the data itself | Rewards/penalties from environment feedback |
| Data required | Labeled data (expensive, slow to produce) | Unlabeled data (plentiful, cheap) | Many interaction episodes, often simulated |
| Learns by | Minimizing prediction error vs. labels | Discovering clusters/patterns/outliers | Trial-and-error to maximize reward |
| Typical security use cases | Spam/phishing classification, malware family labeling, fraud labels | Anomaly detection, network traffic baselining, insider-threat outliers | Automated decision-making, agentic tooling, RLHF for LLM alignment |
| Key risks | Labeling cost; label quality/poisoning; fails on unseen classes | Hard to interpret; false positives on unusual-but-legitimate behavior; no ground truth | Reward hacking; misaligned objectives; huge iteration counts |

- Adjacent paradigms worth one line each (not in the objective list): **semi-supervised** (some labeled + some unlabeled examples) and **self-supervised** (targets generated from the inputs themselves — how LLMs pre-train on unlabeled text).

## Federated Learning

- A **collaborative training approach designed to protect data privacy**: models train directly **where the data resides**; raw data never leaves its owner.
- Workflow (know the order):
  1. A **central server** sends an initial **global model** to many devices or organizations.
  2. Each participant trains a **local copy** of the global model **using its own data**.
  3. Each local model sends **model updates — not raw data** — back to the central server.
  4. The server **aggregates** the updates to improve the global model.
  5. The updated global model is sent back to the participants, and the cycle repeats **until convergence** — the point where the model stabilizes and training stops.
- Benefits: **reduces privacy risk** (sensitive data is never sent to the central server) and **enables regulatory compliance** — the reason it appears in healthcare/finance/multi-org scenarios.
- Security angles (beyond the objective's listed items):
  - A malicious participant can submit **poisoned model updates** — the aggregation server must be able to reject bad updates.
  - Model updates themselves can leak information about local training data (membership inference / gradient leakage).
  - The central aggregation server is a high-value target — protect it accordingly ([[13. AI Access Controls|Module 13]], [[14. Encryption and Data Safety|Module 14]]).

## Model Validation

- The process of **testing a model on new data** — data it has not seen during training — to ensure it learned **generalizable** patterns rather than over-learning the training set.
- **Overfitting**: the model is too closely tailored to the training data (it memorizes noise and quirks) and **fails to generalize to unseen data**.
  - Signature symptom: excellent performance on training data, poor performance in production.
- **Concept drift**: the patterns in the data **change over time** — user behavior shifts, system configuration changes, attacker techniques evolve — so a model may no longer identify current patterns.
  - A model trained on older data may **miss, or misclassify, more recent data**.
- Distinguish the pair (classic exam question): **overfitting is a training-time failure** (memorized the data); **concept drift is a world-change failure** (the data moved on after training). Same symptom — degrading accuracy — different cause and different fix.
- Validation practice (from the foundational notes):
  - **Hold out** part of the available data and never train on it; measure performance against it. In-sample performance (on training data) is not evidence of real-world performance.
  - In practice the data is split so performance is always measured on data the model never learned from:
    - **Training set** — the model fits its parameters to this.
    - **Validation/held-out set** — checks generalization while developing (and tunes choices such as the number of epochs).
    - **Production traffic** — the real test; ongoing monitoring against live data is how drift is caught early ([[15. AI Monitoring and Auditing|Module 15]]).
  - Performance is judged on more than accuracy: **generalization** (unseen data), **explainability/transparency**, and **trustworthiness** — all four matter for security tooling you must defend to auditors ([[15. AI Monitoring and Auditing|Module 15]]).
- Remedies for drift and overfitting: retrain or fine-tune on current data, validate with held-out data, and monitor for decay in production — the feedback loop in [[06. Security in the AI Lifecycle|Module 06]].

## Fine-Tuning: Transfer Learning, Epochs, Pruning, and Quantization

- **Fine-tuning** adapts a model for specific tasks: an existing trained model is **retrained on a smaller, task-specific dataset**, in a process known as **transfer learning**.
- Security value: a pre-trained model fine-tuned on your telemetry learns your **unique threat environment** — your logs, your traffic, your labels — far better than a generic model.
- Fine-tuning on current data is also the practical fix for **concept drift**, and disciplined fine-tuning (with validation) keeps **overfitting** in check.

| Technique | What it changes | Main benefit | Security angle |
| --- | --- | --- | --- |
| Epoch tuning | Number of full passes over the training data | Balances under- vs. overfitting | Too many epochs memorize the training set — including any poisoned examples |
| Pruning | Removes low-contribution weights/neurons | Smaller, faster, less overfitting | Smaller artifact is easier to steal and inspect |
| Quantization | Lowers numeric precision of values | Smaller/faster with near-lossless accuracy; enables edge deployment | Behavior can shift subtly — re-validate; portable artifact is easier to exfiltrate |

### Epoch

- An **epoch is one full pass over the entire training dataset** during training (the data is typically consumed in batches per iteration).
- The tuning tension: **too few epochs and the model underfits** (has not learned enough); **too many epochs and it overfits** (starts memorizing the training data, degrading unseen-data performance).
- Exam framing: epoch tuning is a balance, validated against held-out data — watch where validation performance peaks and stops improving.

### Pruning

- **Reduces model complexity in a neural network by removing weights or neurons that contribute little to performance.**
- Effects: smaller model, faster inference, lower resource cost, and less capacity to memorize noise (an overfitting countermeasure).
- Security angle: a **smaller model is easier to steal, copy, and inspect** — a pruned model shipped to endpoints is a more portable, exfiltratable asset. Guard model artifacts ([[10. Model Extraction and Information Leakage Attacks|Module 10]]).

### Quantization

- **Improves efficiency by lowering the precision of the numerical values used in computations** — e.g., representing weights with fewer bits instead of full-precision floats — making the model **smaller and faster while maintaining nearly the same level of accuracy**.
- Security angles:
  - Enables **on-device / edge deployment**, which keeps sensitive data local (a privacy win — pairs with the SLM story in [[01. Types of AI|Module 01]]).
  - Like pruning, a smaller, self-contained model is **easier to extract and reverse-engineer**.
  - Reduced numeric precision **can subtly change behavior and affect robustness** — re-validate a quantized model before trusting it in production ([[15. AI Monitoring and Auditing|Module 15]]).

- Exam pair: **pruning removes structure (weights/neurons); quantization reduces numeric precision.** Both shrink the model; neither is "compression of the training data."

## Exam Focus

- **Objective wording (learn verbatim):** "Compare and contrast various AI types and techniques used in cybersecurity" — with model validation, supervised/unsupervised/reinforcement learning, and fine-tuning (epoch, pruning, quantization) as the listed training-technique items.
- **Compare/contrast pairs to master:**
  - Supervised vs. unsupervised vs. reinforcement (training signal: labels / none / rewards).
  - Classification vs. regression (categorical vs. continuous prediction).
  - Overfitting vs. underfitting (too tailored vs. not learned enough).
  - Overfitting vs. concept drift (training-time memorization vs. the world changed).
  - Validation data vs. training data (held out vs. learned from).
  - Pruning vs. quantization (remove weights/neurons vs. lower numeric precision).
  - Fine-tuning vs. pre-training (task-specific adaptation vs. foundation-model training).
  - Epoch vs. batch (full dataset pass vs. subset per iteration).
- **Classic distractor confusions:**
  - Federated learning is **not** in objective 1.1's item list — but keep it: privacy/residency and multi-org collaboration scenarios love it. Expect it as the right answer where "raw data never leaves the participants" is the constraint.
  - Fine-tuning vs. RAG vs. prompt engineering: three different adaptation layers (weights vs. retrieved context vs. instructions) — see [[05. RAG|Module 05]] and [[03. Prompt Engineering|Module 03]].
  - Clustering is **not** classification: no labels, no predefined classes.
  - "Model performs well on training data but poorly in production" = **overfitting**, not concept drift; "accuracy decayed over months as attacker techniques evolved" = **concept drift**.
  - Quantization changes precision — it does **not** remove neurons, and pruning does **not** round numbers.
  - Phase-match the attacks: poisoning and backdoors target the **training** phase; prompt injection, evasion, and extraction target **inference** ([[08. Data and Training Attacks|Module 08]], [[09. Prompt and Input Manipulation Attacks|Module 09]]).
- **Likely scenario shapes:**
  - SOC with millions of unlabeled logs and no time to label → unsupervised anomaly detection.
  - Vendor model needs adaptation to your environment's telemetry → fine-tuning / transfer learning.
  - Detection quality decays as attackers change techniques → concept drift → retrain/fine-tune on fresh data.
  - Model must run on resource-constrained edge devices → quantization (and/or pruning).
  - Multiple hospitals/banks want a shared model but cannot pool patient/customer data → federated learning.
  - Regulators ask how you know the model generalizes → model validation with held-out data.

## Key Terms

| Term | Definition |
| --- | --- |
| Supervised learning | Training on labeled data — every example contains the correct answer |
| Labeled data | Training examples pairing inputs with their correct outputs (targets/labels) |
| Classification | Predicting a categorical value (spam vs. not spam) |
| Regression | Predicting a continuous value (attack volume forecast) |
| Unsupervised learning | Training on unlabeled data, discovering patterns and outliers without predefined answers |
| Clustering | Grouping similar data points together without predefined labels |
| Dimensionality reduction | Simplifying complex data by removing redundancies and low-value features |
| PCA (Principal Component Analysis) | Linear dimensionality-reduction technique that preserves maximum variance; reveals patterns/anomalies in large data volumes |
| Reinforcement learning (RL) | An agent learns adaptive decisions by acting in an environment and maximizing rewards / minimizing penalties |
| Agent | The decision-making entity in RL that takes actions and receives feedback |
| Reward function | The feedback signal the RL agent learns to maximize |
| RLHF | Reinforcement learning with human feedback — human ratings shape the reward signal, aligning LLM behavior |
| Federated learning | Collaborative training where participants train locally and share model updates (never raw data) with a central aggregator |
| Global model | The shared model improved by aggregated updates in federated learning |
| Convergence | The point at which a model stabilizes and training stops |
| Model validation | Testing a model on new (held-out) data to confirm it generalizes |
| Overfitting | Model too closely tailored to training data; fails to generalize to unseen data |
| Underfitting | Model has not learned enough (e.g., too few epochs) to capture the patterns |
| Concept drift | Patterns in data change over time, degrading a previously accurate model |
| Generalization | How well a model performs on data it did not see during training |
| Fine-tuning | Retraining an existing trained model on a smaller, task-specific dataset |
| Transfer learning | Reusing a pre-trained model's learned patterns as the starting point for a new task |
| Epoch | One full pass over the entire training dataset |
| Batch | The random subset of data used per gradient-descent iteration (SGD) |
| Pruning | Removing weights/neurons that contribute little to performance, shrinking the model |
| Quantization | Lowering the numeric precision of model values, making the model smaller and faster |
| Loss function | Measure of how poorly the model fits the data (e.g., MSE, cross-entropy) |
| Gradient descent | Iteratively adjusting parameters in the direction that reduces loss |
| Training vs. inference | Fitting parameters to data vs. using the fitted model to predict on new data |
| Anomaly detection | Flagging data that deviates from a learned baseline of normal behavior |
| Baseline | The learned model of "normal" against which deviations are judged |
| In-sample performance | How well a model performs on the data it was trained on |
| Secure aggregation | Combining participant model updates (as in federated learning) without exposing any individual participant's updates |

## Self-Check

1. A security team has 10 million firewall logs and no labels. They want to surface unusual traffic without hand-labeling anything. Which paradigm and technique apply?
2. A phishing classifier scores 99% accuracy on its training set but 61% in production. What is the most likely cause, and what should the team have done differently?
3. The same classifier was solid for a year, then detection quality fell after attackers shifted to a new delivery technique. What happened, and what is the fix?
4. A detection model must run on low-power gateways inside the factory network, and the data must never leave the premises. Name two techniques that help, and the model-type decision they pair with.
5. Six hospitals want to jointly train an intrusion-detection model, but patient data regulations prohibit pooling records. Which approach fits, and what never leaves each hospital?
6. In one sentence each: what does an epoch measure, and what happens with too few vs. too many epochs?
7. A colleague says: "We shrank the model by rounding the weights to lower precision." Which technique is that — and which *other* shrinking technique did they *not* use?
8. Why does an SLM "require fine-tuning" while an LLM is described as versatile without prior examples?

### Answers

1. **Unsupervised learning — clustering/anomaly detection.** With no labels, the model learns the baseline of normal traffic and flags outliers that fall outside the clusters; PCA-style dimensionality reduction often precedes it on large volumes.
2. **Overfitting.** The model memorized the training data. They should have validated on held-out data (never trained on), so the gap between in-sample and real-world performance would have shown before release.
3. **Concept drift.** The patterns in the data changed (new attacker techniques); the fix is retraining or fine-tuning on current data and monitoring for decay so drift is caught early.
4. **Quantization** (smaller, faster model with nearly the same accuracy) and/or **pruning** (removing low-contribution weights/neurons) — which pair naturally with deploying a **small language model / compact model on-premises** ([[01. Types of AI|Module 01]]) so data stays local. Re-validate the quantized model before production.
5. **Federated learning.** Each hospital trains a local copy on its own data and returns **model updates only — raw patient data never leaves** the hospital; the server aggregates updates into the global model.
6. An **epoch is one complete pass over the training dataset**. Too few epochs → underfitting (the model has not learned enough); too many → overfitting (it memorizes the training data and generalizes poorly).
7. **Quantization.** The technique they did *not* use is **pruning**, which removes weights/neurons rather than reducing numeric precision.
8. The LLM's scale and enormous general pre-training give it broad zero-shot capability; the SLM is trained on smaller domain-specific data, so it needs **fine-tuning (transfer learning)** on the target niche task to perform well — trading power for cost, privacy, and efficiency.
